Preface

Terraform becomes easier when each declaration has a reason and each command has an observable effect. This book teaches those relationships from the beginning, then carries them into AWS systems, team state, migrations, security, delivery, and organizational operation.

The intended reader can create a folder and edit a file. Command-line use, types, API vocabulary, networking, identity, Git, and operational concepts are introduced before they are required. The examples begin without a cloud account and grow into a small, inspectable reference system called Field Notes.

The course uses optional guided applications with reference directions, rather than mandatory quizzes. Treat the suggested effort as a pacing aid. Read slowly where a prerequisite is unfamiliar, run the smallest experiment that makes the mechanism visible, and distinguish educational models from actual Terraform and AWS evidence.

Baseline: Terraform 1.17.2, HashiCorp AWS provider 6.0.0, AWS CLI v2, PowerShell as the main shell, Python 3.12+ for local tools, Python 3.13 as the function runtime, and Node.js 22+ for the dependency-free browser companion. The provider is deliberately pinned for reproducibility and is not claimed to be the newest. Source review date: November 13, 2026. Review current releases and security guidance before production adoption.

Code fragments are identified in context; complete source lives in the included labs, modules, assets, and scripts. All account IDs and example names are synthetic. The companion has no AWS access. Real deployments require an authorized sandbox, temporary credentials, destination checks, cost review, and a cleanup decision. No real AWS infrastructure was created during authoring.

The README provides installation, reading order, lab mapping, and commands. The verification report separates checks actually executed from service behaviors you must verify in your own environment. The source ledger records partial and unavailable source access honestly. Use the same evidence standard in your own engineering work.

Part: First principles

Start with observable local change, then give the language and AWS identity precise meaning. These foundations remove ambiguity before resource graphs grow.

1. From a changed setting to a reproducible system

Central problem: How do we change infrastructure deliberately, repeat the change elsewhere, and understand what will happen before we authorize it?

You need: the ability to make a folder and edit a text file. This chapter teaches the command-line and cloud vocabulary required by the first experiment. No AWS account is needed yet.

By the end: you can initialize a Terraform working directory, distinguish configuration from state and infrastructure, read a small plan, apply a local change, and remove the local demonstration. The complete runnable example is labs/00-local; its language features are unpacked in Chapter 2.

1.1 The problem before the tool

Imagine maintaining a small internal application. It needs a place to store files, permission to read them, and a service that answers requests. You create the pieces in a cloud console. A month later, a colleague creates a second environment. They remember most settings, choose a different network option, and forget a permission. Both environments have plausible names. Only one works.

The immediate problem is not that clicking is inherently wrong. It is that the intended design, the actual changes, and the evidence of those changes have become separated. A screenshot shows some settings at a particular moment. A checklist describes actions but may omit defaults. A script describes a sequence, but running the sequence twice can create duplicate objects unless its author anticipated that case.

Infrastructure as code puts an important part of the intended design in reviewable text. Terraform adds a planning engine and a record of the objects it manages. The result is a workflow in which a person can propose a change, inspect its consequences, and authorize execution. The text is still a model. It cannot guarantee the application is useful, secure, affordable, or available. Those properties need design and evidence beyond a successful command.

Our recurring example is Field Notes, a fictional service with a health endpoint, private artifact storage, and a release metadata table. We begin with a representation of services that exists only on your computer. Later we provision small AWS components and assemble them into a deployment. Beginning locally separates Terraform's behavior from cloud permissions, network access, and service charges.

1.2 Five nouns that prevent many misunderstandings

A configuration is the set of Terraform language files in a module directory. It describes resources, inputs, expressions, and outputs. A resource is an object Terraform manages through a resource type. An S3 bucket can be a resource. In our local exercise, a built-in resource records a structured value without contacting AWS.

A provider is a plugin that translates between Terraform and an external system's APIs. The AWS provider understands AWS resource schemas and API interactions. Terraform itself handles expression evaluation, dependency planning, and state coordination. This separation explains why installing Terraform does not install every provider, and why upgrading Terraform and upgrading the AWS provider are different changes.

State records Terraform's associations between configuration addresses and managed object identities, together with information needed for future operations. Think of an address book that says which managed object belongs to each declaration. The analogy is limited: state contains considerably more than names and can include sensitive attributes. State is operational data, not a substitute for the configuration and not an automatically authoritative description of every object in an AWS account.

A plan is a proposed set of actions calculated for a particular configuration, inputs, state, provider behavior, and observations. It may propose creating, updating, replacing, or destroying resources. A plan is not an all-purpose forecast of AWS behavior. Permissions can change, quotas can be reached, and external objects can disappear after planning.

An apply executes an approved plan and records the results Terraform can observe. Execution can succeed partially. If Terraform creates a bucket and then a separate operation fails, it does not promise to delete the bucket as a transactional rollback. This is why we will learn recovery as a normal operating skill.

1.3 A useful reconciliation model

Here is a conceptual model, not Terraform source code:

configuration + inputs + prior state + provider observations
                         |
                         v
                    proposed actions
                         |
                      approval
                         |
                         v
                 API operations + new state

Suppose the configuration requests two service records, state contains none, and no remote objects are involved. The initial plan proposes two creates. Applying creates the records in state. Planning again with unchanged inputs proposes no resource changes. If you change a record's replica value, the next plan proposes an update for that record.

The repeatability we care about is convergence: repeated evaluation with the same relevant conditions reaches a stable desired configuration. This is related to idempotence, the property that repeating an operation has the same final effect. Terraform cannot make every provider operation harmless or every external system perfectly consistent. The practical lesson is to seek a stable no-change plan, while understanding the boundaries of the system being managed.

Terraform is not a daemon that continuously fixes drift merely because configuration exists on disk. Someone or some automation must run it. It also manages declared and associated objects rather than discovering every object in an account and taking ownership. Import and discovery tools help with existing infrastructure, but ownership remains an explicit design decision.

1.4 Files, folders, and the terminal

A terminal is a window through which a shell accepts commands. This course uses PowerShell as the primary shell because it works well on Windows and is available elsewhere. Terraform commands themselves are generally the same in Bash and zsh; environment-variable syntax and quoting can differ.

The working directory is the folder a command treats as its starting point. Terraform ordinarily reads the module in that directory. You can change directories, or use Terraform's global -chdir option to select a directory before the subcommand. This course often uses -chdir so there is less ambiguity about which lab a command affects.

An argument supplies additional information to a command. In terraform version, version chooses the operation. In terraform plan -out=review.tfplan, -out=review.tfplan requests a saved plan at that path. A relative path is resolved from the relevant working directory. An absolute path identifies a location from the filesystem root. Put paths containing spaces in quotes.

From the extracted course folder, these commands inspect the first lab:

Get-Location
Get-ChildItem ./labs/00-local
Get-Content ./labs/00-local/main.tf

Get-Location displays your current directory. Get-ChildItem lists entries. Get-Content reads text. None of these commands changes the lab. On macOS or Linux in Bash, the corresponding common commands are pwd, ls, and cat. You do not need to memorize both shells; choose one and keep commands consistent with it.

A shell reports an exit code when a program finishes. Zero ordinarily means success. Nonzero codes need interpretation by that program's documentation. PowerShell exposes the last native program's exit code through $LASTEXITCODE. Later, Terraform's detailed plan mode deliberately uses a nonzero code to mean that changes exist, so treating every nonzero result as the same kind of failure would break the workflow.

1.6 A smallest complete local configuration

Create a scratch directory if you want to type the example yourself. Put only this configuration in main.tf:

terraform {
  required_version = "= 1.17.2"
}

resource "terraform_data" "greeting" {
  input = "Hello, infrastructure"
}

output "message" {
  value = terraform_data.greeting.output
}

The terraform block constrains the CLI version. It does not download a matching executable. The resource block declares a managed object. Its first label, terraform_data, is the resource type; its second label, greeting, is the name within this module. The address is terraform_data.greeting. input is an argument whose value we choose.

The built-in terraform_data resource stores and exposes values through Terraform's own lifecycle machinery. It does not create a file, server, container, or AWS resource. This makes it useful for observing planning and state without adding a cloud prerequisite. Its output attribute contains the stored input value after application.

The output block exposes a value from the module. Its value expression refers to the resource's output. That reference also tells Terraform about a dependency. The word output appears in two roles: the block publishes a module result, while the resource attribute is a field defined by that resource type. Their shared spelling does not make them the same construct.

1.7 Initialize, plan, and apply with intermediate evidence

In the scratch directory, run:

terraform init
terraform fmt
terraform validate
terraform plan -out=first.tfplan
terraform show first.tfplan
terraform apply first.tfplan
terraform output message
terraform plan

init prepares the directory, installs required providers where necessary, and initializes the configured backend. The built-in provider requires no external provider download. fmt rewrites language formatting consistently. validate checks configuration structure and internal consistency using available schemas; it does not verify that AWS credentials work or that a deployment can fit within quotas.

plan -out calculates and saves a particular proposal. show presents its contents for review. The first plan should contain one resource creation. Some values, such as the resource identifier, are unknown until application. An unknown is an intentional part of Terraform's model, not an error or a missing string that you should replace manually.

apply first.tfplan executes the saved plan. Supplying a saved plan counts as approval; Terraform does not offer the usual interactive yes/no approval step for that plan. Treat the command itself as the authorization boundary. In this local demonstration the effect is small, but the same command structure can operate on production infrastructure.

output message should display the greeting. A subsequent plan should report no changes. That second plan matters: it checks convergence for the conditions observed during the run. It does not certify that every future run will be unchanged.

The generated state contains the managed record. The .terraform directory holds local working data. A dependency lock file may be absent when no separately installed provider is needed. This is normal. Do not invent a provider dependency merely to force a lock file into a local demonstration.

1.8 Observe one controlled change

Change the input string to Hello, Field Notes, then plan again. The resource address remains terraform_data.greeting. Terraform can associate the declaration with the existing managed object and propose an update to its input. The output changes because it depends on the updated value.

Now consider a different edit: rename the resource label from greeting to welcome and update the output reference. You may intend only a cosmetic rename, but the configuration address has changed. Without migration information, Terraform sees one address removed and another added. For a cloud resource this can turn a harmless organizational edit into a destructive proposal. Chapter 8 teaches moved blocks, which preserve identity while changing addresses.

The key relationship is worth stating precisely: labels help form Terraform identity; arguments configure the object represented by that identity. An AWS tag called Name is another piece of metadata and does not replace Terraform's address. Later, a provider-specific immutable argument can also force replacement even when the address stays unchanged. Both address changes and immutable-attribute changes matter during review.

The course's labs/00-local/main.tf manages a map of service records. A map associates stable keys such as api and worker with values. Each value contains a replica count and an enabled flag. The lab filters out disabled services and uses for_each to manage one resource instance per remaining key.

1.10 Clean up deliberately

To remove the records from the local lab:

terraform -chdir=labs/00-local plan -destroy -out=cleanup.tfplan
terraform -chdir=labs/00-local show cleanup.tfplan
terraform -chdir=labs/00-local apply cleanup.tfplan

A destroy plan proposes removing all managed resources selected by that root module and state. It does not search your disk or account and delete unrelated objects with similar names. Conversely, removing a resource declaration from configuration normally proposes destroying its associated managed object. “I deleted a line of code” can therefore represent an infrastructure deletion request.

Do not use deletion of the state file as cleanup. That removes Terraform's record while leaving actual remote objects behind. With cloud resources, you would lose useful associations and could continue paying for unmanaged infrastructure. Even for this local lab, following the normal plan-and-apply lifecycle builds the right habit.

1.11 Review is a technical activity

When reading a plan, start with the account, environment, and state identity. Then inspect resource addresses, action types, important before-and-after values, and unexpected replacements or deletions. A summary such as “3 to add, 1 to change, 0 to destroy” is helpful but insufficient. A single change to an access policy can be more consequential than twenty harmless resource creations.

Unknown values require thought. A planned bucket identifier can be unknown because AWS will assign a suffix. That is expected. A critical policy whose full content becomes unknown because of unnecessarily broad dependencies may deserve a design improvement. The objective is not to eliminate every unknown, but to know which facts the reviewer can establish before application and what needs verification afterward.

Keep operational outputs as evidence. For local learning, notes about the command, selected lab, and observed result are enough. In a team, useful evidence includes the commit, dependency lock file, selected inputs, plan, approval, executor identity, and post-deployment checks. Later chapters build that chain without assuming a particular commercial platform.

Use a separate scratch directory to create a local release record. Give it an input object with service = "field-notes" and release = "v1", then publish that object as an output. Apply once, change the release to v2, and inspect the next plan before applying.

Worked comparison: three edits that look equally small

Use the greeting configuration to distinguish three different changes. First, edit only the input text. The address remains terraform_data.greeting, and the resource type supports updating its stored input. The plan therefore has an existing association and a changed value. This is the simplest configuration update.

Second, edit only the output label from message to greeting_message. The managed resource address and input are unchanged. The published module interface changes, so a caller or operator using the old output name must adapt, but there is no reason to recreate the underlying resource. An output change can be operationally important even when the resource action summary is empty.

Third, edit the resource label and update the reference. The intended message may be identical, but the address association changes. Without a move declaration, the plan can propose removing the old managed instance and creating a new one. The remote or local object ID can change even though the visible text does not.

This comparison gives you a practical way to read future diffs. Ask whether the edit changes a configured value, a published interface, or an identity. Some changes affect several at once. Separating them during learning makes later combined changes easier to reason about.

A source-control habit before the cloud labs

Version control records intentional source changes. Before adding the course to a repository, inspect .gitignore and the actual staged file list. Review contents as well as patterns.

Keep the source and a short note of the observed relationship. You might record that the first plan created one resource, the second unchanged plan converged, and a value edit preserved its ID. 2. HCL as a language for values, relationships, and identity

Central problem: How do we express many related infrastructure objects without losing the ability to understand their values and identities?

Prerequisite: Chapter 1's configuration, resource, state, plan, and apply model. Use the local lab throughout. None of the experiments in this chapter requires AWS credentials.

Outcome: you can read and write blocks and expressions, design typed inputs, transform collections, choose stable instance keys, and explain why some values are unavailable until application.

2.1 Begin with a value, not a loop

A conventional program often tells a computer to perform statements in an order. A Terraform configuration describes a set of relationships. Before introducing resources in bulk, we need a reliable way to describe values. That is the job of expressions in HashiCorp Configuration Language, usually abbreviated HCL in this context.

Consider a replica count of two. The number 2 is a value. The quoted text "2" is a string. They can look similar when printed, but they communicate different intentions to a type system. A service name is text; a replica count is a quantity; an enabled flag is a Boolean. Choosing the right type makes invalid combinations easier to reject near the source of an error.

HCL's infrastructure-specific behavior comes from Terraform's schemas and evaluation rules. HCL alone does not know what an S3 bucket is. A provider defines which arguments a particular resource accepts, which attributes it exports, and which values are computed. This is why a configuration that is visually well formatted can still be invalid for the selected provider.

The practical pattern throughout this chapter is input value → transformation → resource argument → output. Keep those stages visible. If a reader must mentally execute several nested comprehensions just to discover a resource's name, the expression can probably be made clearer with a named local value.

2.2 Blocks and arguments are different structures

A block has a type, optional labels, and a body. An argument assigns an expression to a name. Here is a complete no-cloud module you can place in an empty scratch directory:

terraform {
  required_version = "= 1.17.2"
}

variable "service_name" {
  type    = string
  default = "field-notes"
}

resource "terraform_data" "service" {
  input = {
    name     = var.service_name
    replicas = 2
    enabled  = true
  }
}

output "service" {
  value = terraform_data.service.output
}

variable "service_name" is a block with one label. type = string is an argument within that block. The braces after input = enclose an object expression, not a nested configuration block. This distinction becomes important when provider documentation says an argument expects an object versus a block expects a particular nested structure.

HCL permits compact single-argument blocks, but this course generally uses multiple lines for anything substantial. Do not put two block arguments on a single line separated by a space and assume they form valid syntax. Formatting is not a substitute for parsing. terraform fmt can normalize valid syntax, but it cannot reliably infer the missing structure of an invalid block.

All ordinary .tf files in a module directory contribute to one configuration. A file called variables.tf is a human convention; it has no special evaluation phase. Defining a resource in a.tf does not make it execute before a dependency in z.tf. This gives you freedom to organize by responsibility while preserving the same graph of relationships.

2.3 Learn expressions at the console

The Terraform console evaluates expressions in the current module's context. After initializing the local lab, launch it:

terraform -chdir=labs/00-local console

Type one expression at a time:

2 + 3
upper("field-notes")
length(["api", "worker"])
{ name = "api", replicas = 2 }.replicas
contains(["dev", "stage", "prod"], "dev")

The corresponding results are 5, "FIELD-NOTES", 2, 2, and true. Use exit to leave the console. The console is valuable because it isolates expression behavior from provider operations. It is not a place to enter resource declarations, and evaluating an expression there does not apply infrastructure changes.

A function accepts inputs and returns a value. length counts the elements in a collection or characters in a string under Terraform's string semantics. contains checks membership in a list, tuple, or set; it is not a general substring search. Function names are interfaces with defined type requirements. Guessing that a familiar function behaves exactly like one in another language is a common source of subtle errors.

2.4 Primitive types and structured types

Terraform's primitive categories include string, number, and bool. Structured values include collections and structural types. A list is ordered and normally has one element type. A set represents unique values without meaningful order. A map associates string keys with values of a common type. A tuple has positional elements whose types can differ. An object has named attributes with specified types.

NeedUseful typeWhy
Ordered deployment stepslist(string)Position is meaningful
Unique feature namesset(string)Membership matters, ordering does not
Environment to account mappingmap(string)Stable keys identify entries
One service specificationobject({...})Attributes form a declared contract
Catalog of service specificationsmap(object({...}))Keys identify services; objects describe them

These are semantic choices, not formatting preferences. Converting a list to a set can discard duplicates and ordering. That can be correct for a set of independent names and wrong for a priority sequence. Terraform may perform type conversions where permitted, but relying on implicit conversion can hide an unclear input contract.

The local lab uses the following contract:

variable "services" {
  type = map(object({
    replicas = number
    enabled  = optional(bool, true)
  }))

  default = {
    api    = { replicas = 2 }
    worker = { replicas = 1 }
  }
}

The outer map provides stable identity keys. Each object must have a numeric replica attribute. The enabled attribute is optional and receives true when omitted under this declaration. A caller can therefore write a short specification without losing the module's consistent internal shape. This is preferable to scattering repeated “if missing, then true” expressions throughout resource definitions.

A type constraint specifies a shape, not every business rule. A number can still be negative or fractional. We add validation to express restrictions the type alone cannot express. Also remember that object conversion can discard additional attributes in some conversions; a declared object type is not a universal unknown-key detector. If accidental extra keys are dangerous, choose an additional validation or review strategy suitable to the input format.

2.5 Validate at the boundary

A useful error explains what the caller should change. The local lab rejects replica values that are negative or fractional:

validation {
  condition = alltrue([
    for service in values(var.services) :
    service.replicas >= 0 &&
    floor(service.replicas) == service.replicas
  ])
  error_message = "Replicas must be nonnegative integers."
}

This is a fragment inside the services variable block. values extracts the map's values. The for expression transforms each service object into a Boolean. floor rounds down, so an integer equals its floor. alltrue requires every resulting Boolean to be true. For replicas 2 and 1, the intermediate list is [true, true]. For 2 and -1, it includes false and validation fails.

The difference between a helpful boundary and a brittle restriction is intent. Rejecting negative replicas reflects the domain. Restricting an AWS region to a hard-coded short list because the author remembers only three regions creates needless maintenance. Validate stable requirements, then rely on the provider and service where the accepted domain is inherently service-dependent.

Validation diagnostics should not disclose secrets. An error such as “invalid password: <actual value>” can leak data to logs. Describe the violated rule rather than echoing sensitive inputs. Chapter 9 extends this principle into the entire state-and-plan workflow.

2.6 Variables, locals, and outputs form an interface

An input variable is a parameter supplied from outside a module. A local value names an expression inside the module. An output publishes a selected result. These roles are easy to blur if every expression becomes a variable or every resource attribute becomes an output.

Use a variable when a caller should make a meaningful choice. Use a local when the module should derive a value consistently. Use an output when another module or operator has a legitimate reason to consume the result. For example, the caller can choose the environment, the module can derive a naming prefix, and an output can publish the resulting bucket name.

variable "environment" {
  type    = string
  default = "dev"
}

locals {
  service_prefix = "field-notes-${var.environment}"
}

output "prefix" {
  value = local.service_prefix
}

This is a complete expression-only configuration when combined with the chapter's Terraform version block. String interpolation inserts an expression inside text. The resulting prefix for the default environment is field-notes-dev. The local has no separate persisted identity merely because it has a name; it is an expression result.

The reference prefixes are deliberately different: var.environment, local.service_prefix, and resource addresses such as terraform_data.service. These prefixes tell a reader where a value originates. Do not turn a literal into a variable solely to avoid writing the literal once. An unnecessary parameter expands the interface without adding a useful decision.

2.7 Input sources and repeatable runs

For a local CLI workflow, values can come from defaults, environment variables named TF_VAR_name, variable definition files, and explicit command-line assignments. Precedence matters when more than one source supplies a value. Keep a project's documented entry point and input files explicit rather than depending on whatever happens to be set in a shell.

terraform -chdir=labs/00-local plan -var='environment=stage'
terraform -chdir=labs/00-local plan -var-file=stage.tfvars

The second command assumes you have created stage.tfvars in the lab directory. A variable file uses assignments such as environment = "stage"; it does not wrap them in a variable declaration. The file is configuration data, not a second module. Terraform loads specifically named automatic variable files by convention, so a forgotten local file can influence later plans.

PowerShell environment syntax is $env:TF_VAR_environment = "stage"; Bash uses export TF_VAR_environment=stage. Remove the variable when you no longer want it to apply. In PowerShell, Remove-Item Env:TF_VAR_environment removes it from the current process environment. Do not place real credentials in a variable file just because the filename ends in .tfvars.

The course ignores real local terraform.tfvars files in version control and distributes .example files with synthetic values. Some nonsecret environment settings can reasonably be committed in a team repository. Decide based on the contents and workflow, not the extension alone. Record which inputs a saved plan used so its review is reproducible.

2.8 Transform collections one stage at a time

The local lab filters disabled services:

locals {
  active = {
    for name, service in var.services :
    name => service if service.enabled
  }
}

For the defaults, active has both api and worker. If the worker has enabled = false, the result has only the API entry. The expression preserves the original keys rather than converting the result into a position-based list. That matters because the next stage uses those keys as resource identity.

A for expression calculates a value. It does not issue an API operation for every iteration. Terraform evaluates the resulting collection, then uses resource and module declarations to construct managed instances. Keeping expression transformations separate from resource repetition makes the configuration easier to debug.

For another example, a list of enabled service names can be derived with [for name, service in var.services : name if service.enabled]. A list of readable labels can be derived with [for name in keys(local.active) : "service:${name}"]. Start with the simplest intermediate value at the console before composing several transformations. Small intermediate observations are often faster than reading a long provider diagnostic caused by a malformed final object.

2.9 Resource repetition is identity design

The local lab declares resources with for_each:

resource "terraform_data" "service" {
  for_each = local.active

  input = {
    name        = each.key
    replicas    = each.value.replicas
    environment = var.environment
  }
}

each.key is the current stable service name. each.value is its specification. The result is a set of instances addressed by key. Updating the API replica count keeps the API address. Removing the worker key removes that instance from the desired set. Adding a new key creates a new managed identity.

The alternative count creates numbered instances. For a simple optional singleton, count = var.enabled ? 1 : 0 can be readable. For an ordered list whose elements may be inserted or removed, positions can be fragile. If ["api", "worker", "scheduler"] supplies names to count-based resources and you remove worker, index one now means scheduler. Terraform associates identity with the numeric index, not with the name you mentally attached to that position.

ChoiceAddress formSuitable use
Singletonresource_type.nameOne persistent object

For eachresource_type.name["api"]Objects with meaningful stable keys

Switching between these forms changes addresses and often needs explicit migration. Choosing for_each does not make renaming keys free. A key change from api to public-api is an identity change unless a moved declaration establishes continuity. Chapter 8 provides an executable migration lab.

2.10 Known, unknown, null, and sensitive are separate ideas

A known value is available during the relevant evaluation phase. An unknown value is not yet available, often because a provider will return it after resource creation. Null represents absence or omission in contexts that allow it. A sensitive value carries metadata used to restrict normal display. These categories answer different questions.

A generated bucket name can be unknown during planning. That does not mean it is null. An optional argument set to null can tell Terraform to omit a value, allowing a provider default where supported. A sensitive value can be fully known to Terraform and still be hidden from ordinary output. None of these concepts is equivalent to encryption.

for_each keys must be available early enough to establish instance addresses. Use a known map of service names even when the values contain future resource IDs. Trying to use newly generated IDs as instance keys fails because Terraform cannot establish the instance set before those IDs exist. This is an evaluation constraint with a design consequence: choose identity from stable intent, then carry computed details as values.

Avoid using sensitive material as keys. Resource addresses are routinely exposed in plans, logs, and diagnostics. An API token is a poor instance key even if the language allowed your intended construction. A nonsecret logical key such as payments makes the identity safer and easier to review.

2.11 References define dependency edges

When a resource argument refers to another resource's attribute, Terraform can infer that the second resource must provide the required value. This is an implicit dependency. It usually expresses the true reason for the ordering more accurately than a broad depends_on list.

A dependency graph is a set of nodes connected by directed relationships. Terraform can execute independent operations concurrently while respecting required order. File position is irrelevant. A bucket policy referring to the bucket ARN depends on the bucket value even when the policy appears first in the file.

Use explicit depends_on for a real hidden dependency that values do not express. For example, a function may require its logging policy to be attached before successful execution, even though its configuration refers directly only to the role ARN. This does not guarantee that every distributed AWS system is instantly consistent; it establishes Terraform's ordering relationship.

Broad module-level dependencies can make many downstream values unknown and reduce parallelism. Adding them to silence a symptom without identifying the actual hidden dependency often makes plans harder to review. Ask what fact or readiness condition the operation actually needs, then model the narrowest accurate relationship.

2.12 Conditionals and defensive expressions

A conditional has the form condition ? true_value : false_value. Both alternatives must be compatible with the surrounding type expectations. A conditional is useful for a deliberate choice, such as a retention period selected by environment. It should not become a substitute for clearly different architectural modules.

try and can help handle expressions that may raise dynamic errors. can(regex(...)) is useful when validating a string format. try is most useful while normalizing uncertain external data into a predictable internal shape. Repeating try around every resource argument can hide misspelled attributes and produce plausible defaults that conceal a real bug.

Do not assume Boolean operators short-circuit every invalid expression the way you expect from another language. A null or malformed value can still require an explicitly safe conditional or normalization. For example, validate the presence and shape of an optional object before dereferencing its attributes through an unsafe expression. Test the expression with representative null and missing values in the console.

Prefer jsonencode when building JSON for an IAM policy or API payload. It converts HCL values into correctly escaped JSON. Hand-built JSON strings are easy to break with quotation marks and interpolation. A provider-specific policy-document data source adds additional structure for IAM policies, which Chapter 3 introduces.

2.13 Dynamic blocks have a narrower purpose

A dynamic block generates repeated nested blocks where a provider schema requires them. It does not create top-level resources, and it does not make unsupported resource arguments valid. Use ordinary expressions for ordinary collection arguments; use resource for_each for resource instances.

Dynamic blocks can be appropriate for a small, well-understood list of nested rules. They can also obscure a schema behind a generic abstraction. A module that accepts an arbitrary copy of every nested provider option may offer little value beyond making the official documentation harder to map to the code.

We will use explicit resource types for security group rules and ordinary map transformations for service catalogs. This is a teaching choice that makes ownership visible. When you encounter dynamic blocks in a real repository, identify the required nested block type, the collection being iterated, and the mapping from each element into the generated body.

2.15 Debug expressions by reducing uncertainty

When an expression fails, identify whether the problem is syntax, type, shape, timing, or identity. A missing equals sign is syntax. A list passed where an object is expected is type or shape. A computed resource ID used as a repetition key is timing. A renamed map key producing a destroy/create proposal is identity.

Use terraform console to inspect a small value. Use type(...) in the console when you need to understand a value's type. Build a transformation in stages with locals while debugging, then keep the intermediate names that clarify intent. Do not hide a failure behind an empty default until you understand whether an empty result is a legitimate business case.

A good diagnostic path for an invalid for_each begins with the instance keys: are they strings, stable, nonsecret, and known at plan time? Then inspect the values. Many advanced-looking failures are a mismatch between the intended identity scheme and the data structure chosen to represent it.

2.16 Optional application and reference approach

Extend the local catalog with a scheduler service, enabled only in stage. Add a computed output listing service names and total desired replicas. Keep the same service keys and validate the replica domain. The reference approach is to construct the input map explicitly for the chosen environment or use a conditional for the scheduler's enabled attribute, filter it through the existing active map, and sum active replica counts.

An appropriate total expression is sum([for service in values(local.active) : service.replicas]). With API two and worker one, the total is three. If scheduler has one replica and is active in stage, the total is four. This total is a calculation over declarations; it remains distinct from observing runtime capacity.

In the companion, the Collection identity experiment computes address changes when an element is inserted into a list or a key is added to a map. Use it to see why stable keys reduce unintended reassociation. Its model deliberately excludes provider-specific replacement rules, which the change-management chapter adds to the discussion.

Worked normalization: accept a choice, derive one internal shape

Suppose a caller may optionally provide a display name for a service. A useful design is to keep the stable service key separate from its human-readable label. The key might remain api while the display name becomes Public API. Renaming the display name then changes metadata without changing the instance address.

A typed object can declare display_name = optional(string). A local expression can choose the supplied value when it is non-null and otherwise derive a readable label from the key. Keep that normalization near the input boundary, then let every resource consume the normalized shape. This avoids inconsistent defaults scattered across several resources.

The same pattern applies to tags, retention, and optional configuration. The contract accepts a bounded choice; the local transformation makes the internal representation predictable; resource repetition continues to use stable keys. Do not derive identity from a display label merely because the label happens to be unique today.

When debugging, inspect the raw input and normalized local separately. If the raw object is correct but the normalized value is wrong, the failure is in transformation. If the local is correct but a provider rejects the argument, inspect the resource schema and service constraint. This small separation turns one large mystery into two observable boundaries.

3. AWS identity, permissions, and the first private bucket

Central problem: How can Terraform create the intended object in the intended account, using an identity with appropriate authority, without turning credentials or data into public artifacts?

Prerequisites: Chapters 1–2. This chapter introduces AWS accounts, regions, APIs, temporary credentials, IAM, and S3 before using them. You can read and inspect the source without an AWS account; applying the lab requires a sandbox account you control and may incur charges.

Runnable source: labs/01-bucket. The more complete reusable storage contract appears in modules/private-bucket.

3.1 A cloud account is an authority and billing boundary

AWS is a collection of services accessed through APIs. An API is a defined interface through which a program makes requests and receives results. The AWS console is one client of those interfaces, the AWS CLI is another, and the Terraform AWS provider is another. A setting changed through any of them can affect the same underlying object.

An AWS account contains resources, identities, service limits, and billing relationships. It is not the same as an individual person's login. An organization can give many people and automation systems access to an account. A region is a geographic service area with its own regional resource scope. An Availability Zone is an isolated location within a region. Different service types have different scopes: an IAM role is not a subnet, and a bucket name has naming constraints that differ from a local Terraform label.

We use us-east-1 in examples so that values remain consistent. This is a convention, not a claim that it is the right region for your data, latency, compliance, or business continuity requirements. When changing regions, inspect every dependent assumption, including zone names, service availability, endpoints, images, and costs.

Before any real apply, establish the account and region explicitly. A friendly profile name like sandbox is helpful but not proof of the destination. Profiles can be edited, environment credentials can take precedence, and a shell can retain settings from another task. We add an account allowlist in the provider so that a misdirected run fails early.

3.2 Authentication and authorization answer different questions

Authentication establishes who is making a request. Authorization decides whether that identity may perform a particular action on particular resources under particular conditions. A valid login does not imply permission to create an S3 bucket. A successful S3 listing does not imply permission to modify IAM.

AWS IAM expresses permissions through policies, roles, and related mechanisms. A role is an identity that can be assumed under a trust policy and used through temporary sessions. A trust policy governs who may assume the role. A permissions policy governs what the resulting role session can do. These are different boundaries. A perfectly narrow permissions policy is useless if nobody legitimate can assume the role; an overly broad trust relationship can expose the role's permissions to an unintended principal.

For human access, the course prefers federation through IAM Identity Center or your organization's equivalent temporary-credential flow. For workloads, prefer role-based temporary credentials. The AWS IAM guidance supports these patterns and least-privilege access. Protect the account root user for account-level administration rather than using root credentials for Terraform labs.

A course cannot supply your organization's login URL, permission set, or role trust relationship. Those values must come from your account setup. If you do not yet have a safe AWS environment, continue with the local labs and companion while arranging one. Do not guess corporate account credentials or reuse a production profile merely to make an example run.

3.3 Configure and prove a temporary session

Install AWS CLI v2 using AWS's official installation instructions for your platform. If your account uses IAM Identity Center, the following is the common interactive flow:

aws --version
aws configure sso --profile terraform-learning
aws sso login --profile terraform-learning
aws sts get-caller-identity --profile terraform-learning

The configuration wizard asks for organization-specific SSO and role information. The login opens the appropriate sign-in flow. sts get-caller-identity returns the account identifier and caller identity. It is an identity diagnostic, not a permissions audit and not an instruction to publish the returned details.

Select the profile for the current PowerShell session:

$env:AWS_PROFILE = "terraform-learning"
$env:AWS_REGION = "us-east-1"
aws sts get-caller-identity

In Bash, use export AWS_PROFILE=terraform-learning and export AWS_REGION=us-east-1. The profile is not a secret, but the temporary credentials behind the session are sensitive. Do not paste access keys into Terraform source. If environment variables contain an old access key and secret, they can influence which identity a client uses. Diagnose the credential chain deliberately rather than repeatedly signing in to different profiles.

The precise SSO setup depends on prerequisites in your account. AWS documents the required configuration and session behavior in IAM Identity Center authentication for the CLI. The course does not create accounts, identities, or permission sets on your behalf.

It cannot prove that the account is yours or that it is a sandbox. The provider's allowlist compares the authenticated account against the value you supplied. 3.5 Understand S3 before creating a bucket

Amazon S3 stores objects inside buckets. An object consists of data and metadata addressed by a key. A key such as notes/intro.txt looks like a filesystem path, but S3 does not become a conventional mounted directory tree because keys contain slashes. Service APIs and permissions operate on buckets and objects with distinct resource identifiers.

A bucket name has service-wide naming requirements and uniqueness constraints within the applicable AWS partition. A Terraform label such as notes only needs to be unambiguous within its module and resource type. The lab uses a bucket prefix so the provider can generate a suffix rather than assuming a globally available exact name.

Creating a bucket does not upload a file. Enabling versioning does not create an independent backup account. Encrypting at rest does not decide who is authorized to read data. Blocking public access does not remove every possible cross-account grant. Each control addresses a particular threat or operating requirement.

Our first bucket is intentionally small in purpose: private learning storage with versioning and explicit default encryption. The reusable module later adds ownership controls and an HTTPS-only policy. We add these concepts incrementally so each security decision has an explanation and an observable configuration.

3.6 Trace the first resource graph

The lab declares an S3 bucket, a public-access block, versioning configuration, and server-side encryption configuration. The bucket is the parent object. The supporting resources refer to its ID. Those references form dependency edges.

resource "aws_s3_bucket" "notes" {
  bucket_prefix = "tf-mastery-notes-"
  force_destroy = false
}

resource "aws_s3_bucket_public_access_block" "notes" {
  bucket                  = aws_s3_bucket.notes.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

The bucket's id identifies the created bucket for the related resource. The public-access settings are explicit so the desired posture is visible in the configuration rather than merely relying on remembered account defaults. These settings do not grant the Terraform executor permission to do anything; IAM still authorizes the calls.

force_destroy = false means Terraform should not automatically empty a nonempty bucket to destroy it. That is a data-retention choice. It can make cleanup require additional deliberate action, which is appropriate for teaching the difference between removing infrastructure and deleting stored data.

The supporting resources can be planned before the bucket name is fully known because Terraform understands the references. It does not need you to apply the bucket, copy its name, and paste it into the next resource. Manual copy-and-paste would lose the dependency relationship and make the configuration less reusable.

3.7 Versioning and encryption solve different problems

Versioning preserves multiple versions of an object key as the object changes. Deleting a versioned object normally creates a delete marker rather than erasing every previous version. This gives recovery options but also means that “the bucket looks empty” is not sufficient evidence that all versions have been removed.

The lab's encryption configuration requests server-side encryption using S3-managed encryption keys with the AES256 setting. This makes the at-rest encryption choice explicit. A customer-managed KMS key introduces additional control and additional key-policy, availability, and cost responsibilities. It is appropriate when those controls are needed, not automatically superior for every tiny learning bucket.

The important causal distinction is that encryption protects stored data through a key-management mechanism, while authorization governs who may request access. A permitted caller can receive decrypted data through the normal service path. A broad read policy does not become acceptable merely because encryption is enabled.

For Terraform state, encryption is especially relevant because state can contain secrets. A private, encrypted bucket with versioning is part of a backend design, but it still needs carefully scoped access and an operating process. Chapter 6 builds that larger system; do not assume this first bucket is already a complete shared-state platform.

3.10 Read an IAM policy as a bounded decision

An IAM policy statement includes an effect, actions, resources, and optional conditions. Here is an explanatory identity-policy fragment for reading objects under a particular prefix:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject"],
    "Resource": ["arn:aws:s3:::example-learning-bucket/notes/*"]
  }]
}

This is a teaching fragment using a synthetic bucket name; it is not attached by the lab. The action identifies the API permission. The object ARN scopes it to keys under notes/. The bucket ARN without the trailing object path represents a different resource scope. Listing a bucket typically requires a bucket-level permission such as s3:ListBucket, which is why adding a GetObject statement does not automatically make every command succeed.

The full authorization result can involve identity policies, resource policies, permission boundaries, session policies, organization policies, and explicit denies. A small browser experiment cannot implement that entire system. Our companion's Policy reasoning model explicitly covers a simplified allow/deny case to teach the idea of intersecting limits; use AWS IAM tools and documentation for real evaluations.

Least privilege means granting the actions and resources required for the legitimate job under appropriate conditions. It is not achieved by changing one wildcard in an otherwise unexplained policy. Begin with the workflow, identify the actual API operations, scope them, and verify both permitted and prohibited behavior in an appropriate environment.

3.11 Why policy documents are generated from values

The reusable bucket module uses aws_iam_policy_document to construct a policy denying non-TLS requests. The statement references the bucket ARN and object ARN, uses effect Deny, and checks the aws:SecureTransport condition. It then assigns the generated JSON to an S3 bucket-policy resource.

This separates the policy's structured inputs from JSON serialization. An expression such as "${aws_s3_bucket.this.arn}/*" derives the object resource scope from the actual bucket. Terraform can then see the dependency. The data source itself does not grant permissions or create an AWS policy attachment; the consuming resource is what applies the resulting policy to AWS.

A TLS-only deny is a narrow control, not an all-encompassing policy. It does not grant anyone access, and it does not replace public-access blocking. Likewise, object ownership enforcement addresses ACL behavior, while versioning addresses recovery. A sound storage contract composes controls whose purposes you can explain.

When testing with a mocked provider, computed policy-document JSON must still be valid for consumers that validate JSON syntax. Chapter 9 shows why mocks need purposeful defaults and why passing a mock test does not prove AWS accepts a real policy.

3.12 Diagnose failures at the correct boundary

An expired SSO session is an authentication problem. An AccessDenied response is usually an authorization or explicit-deny problem. A naming conflict is a service constraint. A resource already managed elsewhere is an ownership problem. A wrong-region endpoint or an unreachable API is a connectivity or configuration problem. Similar-looking command failures can require very different remedies.

For an authorization failure, record the caller, action, resource, and relevant conditions. Do not immediately attach AdministratorAccess. An apparently broad allow can be limited by an explicit deny or another policy boundary. Increasing permissions without understanding that boundary can fail to fix the issue while increasing risk elsewhere.

For a bucket conflict, distinguish an exact name from a generated prefix. A prefix reduces the chance of a collision; it does not permit violating naming rules. For a destroy failure, inspect whether object versions or delete markers remain. For a provider identity error, compare the actual account with allowed_account_ids before editing the allowlist.

Terraform diagnostics often include request identifiers from AWS. Those can help an account administrator investigate service behavior. Preserve useful diagnostics in a protected place while keeping credentials and sensitive payloads out of public issues. A reproducible failure report should explain the action and context without requiring access to secret values.

3.13 Costs and cleanup are design topics

An empty learning bucket is inexpensive in many situations, but “inexpensive” is not a spending guarantee. Requests, storage, transfers, logs, KMS operations, and related services can be billed. Free-tier eligibility depends on current account programs and usage. This course does not assume that every learner qualifies for a free tier.

Use a budget or billing alert appropriate to your account and understand that an alert does not automatically stop all resource usage. The companion's cost experiment accepts your own rates and labels its output as an estimate. Obtain live prices for the actual region and services before a substantial deployment.

For an untouched empty bucket, a reviewed destroy plan should remove the lab resources. If you uploaded objects after enabling versioning, normal object deletion may leave versions behind. Deliberately inspect versions and delete only the synthetic lab data you intend to discard, including delete markers where necessary. Keep force_destroy = false as the default habit for storage whose data matters.

terraform -chdir=labs/01-bucket plan -destroy -out=cleanup.tfplan
terraform -chdir=labs/01-bucket show cleanup.tfplan
terraform -chdir=labs/01-bucket apply cleanup.tfplan

If a deletion fails, do not delete Terraform state to suppress the error. Resolve the service condition and rerun a normal plan. State preservation is particularly valuable after partial operations because it records which associations Terraform already established.

3.14 Optional application: compare a setting with an invariant

Add a nonsecret Environment tag to the first bucket and plan the change. Observe whether the bucket identity remains the same. Then inspect the reusable private-bucket module and write one sentence for each control explaining which property it aims to maintain.

A reference explanation is: public-access blocking limits public grants; ownership enforcement disables ACL-based ownership ambiguity; versioning preserves prior object versions; encryption defines at-rest handling; the TLS policy rejects insecure transport; force-destroy being false resists automatic deletion of stored contents. None of these sentences should claim that the control independently proves “the bucket is secure.”

For a deeper application, draft an access requirement that separates the Terraform executor from an application reader. The executor manages bucket settings. The application can read only a specific object prefix. This is a design exercise with a clear reference direction, not a requirement to modify a corporate IAM system.

3.15 Connect identity to the network chapter

IAM answers whether an authenticated principal may ask a service to perform an action. Network routing answers whether packets can reach the relevant endpoint. Both can block a workflow, but they operate at different layers. A private subnet does not grant S3 permissions, and a permissive IAM statement does not create an internet route.

Chapter 4 introduces IP addresses, CIDR ranges, subnets, routes, gateways, and security groups in that dependency order. We will build the network as a reusable set of relationships, while keeping paid NAT gateways and always-on compute out of the default network lab. The result is a practical network foundation whose reachability can be reasoned about before any application is placed inside it.

Worked request trace: a private object read

Assume a role session tries to retrieve notes/intro.txt from the learning bucket. First, the client needs a route to the S3 endpoint and a successful authenticated request. Second, the applicable authorization must permit s3:GetObject on the object ARN. Third, explicit denies and relevant limits must not prohibit the request. If a customer-managed encryption key is involved, the necessary key authorization also matters.

The public-access block does not supply the role's allow. It constrains public access behavior. The TLS-only bucket policy does not supply the allow either; it denies a class of insecure requests. The at-rest encryption setting does not choose which role can read the data. Each mechanism has a different causal role in the final result.

Now change only the request to use an insecure transport path. The TLS deny becomes relevant even if the role has an object-read allow. Change only the object key to private/other.txt, and a prefix-scoped allow may no longer apply. Change only the role session, and a different set of identity/session constraints may be evaluated. A useful diagnostic changes one relevant dimension at a time.

For a real failure report, record the action, bucket/key scope, caller role, endpoint context, time, and request identifier where available. Do not include the temporary secret access key. The request can be investigated through its identity and service evidence without distributing the credential that signed it.

An independent service query can also fail because the diagnostic role lacks read access to bucket settings while the deployment role successfully configured them. In that case, the absence of diagnostic permission is not evidence of an absent control. Ask an authorized operator to verify the specific setting or use a purpose-built read role. Avoid broadening an application role to administrative access merely to make a convenience command work.

This trace is the beginning of a security habit used throughout the course: describe the actual request and enumerate the boundaries it crosses. A statement such as “the bucket is encrypted and private” is a useful inventory summary, but it is too broad to explain why one concrete request succeeds or fails.

4. Build a network by tracing a packet

Central problem: How do we determine which components can communicate, and express that design without accidental address overlap or hidden routing assumptions?

Prerequisites: Terraform values and instance keys; AWS accounts and regions. This chapter introduces the necessary networking before the configuration that uses it.

Source: modules/network and labs/02-network. The default lab creates network components and an S3 gateway endpoint, with no EC2 instances, NAT gateways, load balancers, or public IPv4 allocations. This is a deliberate learning topology, not a universal production network.

4.1 Start with delivery, then introduce the address

A computer sends information in packets. At a practical level, a packet includes source and destination addresses, a protocol, and often source and destination ports. A router chooses where to send it next. A firewall decides whether the traffic is permitted. A name service can translate a human-readable name into an address. These are distinct jobs.

Suppose an application needs to read an object from S3. Before debugging Terraform, ask four questions: what endpoint did the application resolve, which route carries its packets, which network controls permit the traffic, and which IAM identity authorizes the object read? A failure in any one can produce an application error. The error message alone may not identify the layer.

An IPv4 address is a 32-bit number conventionally written as four decimal octets, such as 10.42.1.7. Each octet represents eight bits and ranges from zero to 255. You do not need to manipulate binary strings constantly, but understanding the address size explains why network prefixes change capacity in powers of two.

A port identifies a transport endpoint within a host. HTTPS commonly uses TCP port 443. A server listening on port 443 still needs a reachable address and permitted traffic. Conversely, a working route does not create a listener or authorize the application request. Keep these distinctions visible when reviewing security group rules.

4.2 Derive CIDR sizes with a concrete example

CIDR notation writes an address followed by a prefix length. 10.42.0.0/16 means the first 16 of the 32 bits identify the network. That leaves 16 address bits, so the block contains 2^(32 - 16) = 65,536 addresses. A /24 leaves eight bits and contains 256 addresses. A longer prefix means a smaller range.

To divide a /16 into /24 subnets, add eight prefix bits. There are 2^8 = 256 possible subnet slots, numbered zero through 255. Each slot advances the third octet in this particular example. Slot zero is 10.42.0.0/24, slot one is 10.42.1.0/24, and slot 128 is 10.42.128.0/24.

Terraform's expression cidrsubnet("10.42.0.0/16", 8, 128) computes the last range. The arguments are the original prefix, the additional network bits, and the subnet number. The added bits count is not the target prefix length. Passing 24 as the second argument would mean adding 24 bits to the original prefix, which is not the intended calculation.

AWS reserves certain IPv4 addresses in each ordinary subnet, so 256 total addresses do not mean 256 assignable host addresses. For the common subnet rules, five addresses are reserved, leaving 251 in a /24. Service-specific consumption, scaling, and operational headroom further reduce practical capacity. A subnet plan should account for interfaces created by managed services, not just the number of virtual machines you initially expect.

The course uses deliberately roomy ranges for clarity. Real address planning must consider corporate networks, peering, VPNs, and future regions. Overlapping address space can make later connectivity difficult. Creating a small VPC in isolation is easy; fitting it into an organization's address plan is a different engineering problem.

4.3 A VPC contains subnets, and a subnet belongs to one zone

A Virtual Private Cloud is a logically isolated virtual network associated with a region. A subnet is a slice of its address space located in one Availability Zone. Spreading an application across two subnets in the same zone does not provide the same fault separation as using two zones.

The lab takes a map of logical zone keys. Each value supplies an actual zone name and a stable address slot:

zones = {
  first  = { name = "us-east-1a", slot = 0 }
  second = { name = "us-east-1b", slot = 1 }
}

The keys first and second are module identities. The zone names are AWS placement choices. The slots determine CIDR allocation. Keeping these concepts separate lets the module preserve an understandable addressing policy rather than assigning subnets based on incidental list order.

Zone names can map to different physical zones across accounts. For cross-account alignment, AWS zone IDs are the appropriate concept to investigate. This lab uses names within one account and tells you to confirm availability before applying. Merely changing region without changing these zone values is insufficient.

A multi-zone network supports an availability design; it does not automatically make the application highly available. A single database in one zone, a missing second application instance, or an untested failover procedure can remain a single point of failure. Infrastructure topology is one layer of availability evidence.

4.4 Public and private describe routes, not trustworthiness

A public subnet has a route to an internet gateway for relevant internet destinations. A private subnet lacks that direct internet-gateway route. A resource also needs suitable addressing and security settings to communicate as intended. Giving a subnet the tag public does not make it public, and calling a subnet private does not establish a security boundary by itself.

The lab creates one public route table shared by the public subnets. It contains a default IPv4 route, 0.0.0.0/0, pointing at the internet gateway. Each private subnet receives its own private route table. Those tables initially have no default internet route.

The VPC's local route supports communication within the VPC address space subject to the other relevant controls. Route selection generally uses the most specific matching destination prefix. A /24 route is more specific than a /16, and both are more specific than /0. This is called longest-prefix matching.

Consider destination 10.42.129.8. In this lab it belongs to the VPC range, so the local VPC route is relevant. Destination 8.8.8.8 does not belong to that range. In a public route table, the default internet route can be selected. In the lab's private route table, there is no general internet path for that destination.

The companion's CIDR and route explorer calculates subnet ranges and selects the longest matching route from a small explicit route list. It does not simulate AWS appliances, security groups, DNS, or transit networking. Use it to isolate address arithmetic and route choice before combining those layers.

4.5 Trace the module's resource relationships

The module begins with a VPC, enables its DNS features, and attaches an internet gateway. It then creates public and private subnets for each zone key. The public and private CIDR calculations intentionally use different halves of the available slot space.

resource "aws_subnet" "private" {
  for_each          = var.zones
  vpc_id            = aws_vpc.this.id
  availability_zone = each.value.name
  cidr_block        = cidrsubnet(var.cidr, 8, 128 + each.value.slot)

  tags = {
    Name = "${var.name}-private-${each.key}"
  }
}

This is a fragment from the complete module. For first with slot zero, the subnet number is 128 and the resulting range is 10.42.128.0/24. For second with slot one, it is 129. Public subnets use slots zero and one, so the four ranges do not overlap.

The input validation rejects duplicate slots, noninteger slots, and slots outside zero through 127. Those checks protect the mapping between the two halves of the address space. The module explicitly accepts an IPv4 /16; adding eight bits then produces the tested /24 subnet layout. Generalizing that contract requires a new address policy and tests.

The explicit slot field is an architectural promise. Adding a third zone with slot two does not shift the existing ranges. Removing the first entry does not renumber the second. This is an application of the stable-key principle from Chapter 2 to a setting where accidental reassociation can replace infrastructure.

4.6 Associate route tables explicitly

Creating a route table is not enough. A subnet must use the intended route table. The association resources make that relationship reviewable:

resource "aws_route_table_association" "private" {
  for_each       = aws_subnet.private
  subnet_id      = each.value.id
  route_table_id = aws_route_table.private[each.key].id
}

The association iterates over the created private subnets. Each subnet key selects the matching private route table. That is why the same logical keys flow through both collections. The expressions encode a one-to-one relationship rather than relying on matching positions in independently sorted lists.

AWS also has main and default network constructs. Relying on them can make a demonstration shorter but can hide inherited behavior. In a real repository, inspect whether a resource creates a new route table, modifies a default one, or depends on an existing association. Different ownership choices can produce very different plans even when diagrams look similar.

Do not manage the same route simultaneously through an inline route declaration and a standalone route resource when the provider documents conflicting ownership. Terraform configurations need a coherent owner for each managed setting. Two declarations fighting over the same remote property can produce perpetual differences or unintended deletion.

4.7 Understand public IPv4 and NAT before adding them

An internet gateway route alone does not supply an EC2 instance with a public IPv4 address. The lab explicitly sets map_public_ip_on_launch = false on public subnets. A public subnet can host a public load balancer or a deliberately addressed resource without forcing every launched instance to receive a public address.

A NAT gateway allows suitable private-subnet IPv4 traffic to initiate connections through an egress path without giving every instance its own public IPv4 address. It usually introduces hourly and data-processing charges, and a zonal design has availability and cross-zone cost consequences. The lab omits NAT by default because the network concepts can be learned without an always-on paid egress component.

If a production application needs arbitrary outbound internet access from private subnets, the omission must be addressed through a deliberate design. A public NAT gateway typically resides in a public subnet with an Elastic IP and internet-gateway connectivity; private route tables point appropriate traffic to it. A single shared NAT can reduce some fixed costs while creating a wider failure dependency and potential cross-zone traffic. Per-zone NAT can improve fault isolation at greater cost.

The correct choice depends on traffic, availability objectives, service endpoints, and controls. “Always use one NAT per zone” and “always use one NAT to save money” are both incomplete policies without those assumptions. The book's reference network makes the lack of general egress explicit so that a learner is not surprised when a package download from a private host fails.

4.8 An S3 gateway endpoint is a service-specific route

The network module creates an S3 gateway endpoint and associates it with the private route tables. This provides a service-specific path for S3 traffic in the supported context. It does not create arbitrary internet access, and it does not grant S3 object permissions.

The service name is derived from the provider's current region. The endpoint attaches to the VPC and identifies which route tables receive the relevant routing integration. An application still needs a valid IAM identity and applicable bucket permissions. An endpoint policy can add another limit; our introductory endpoint uses the provider/service defaults and is not a complete data perimeter design.

Distinguish gateway endpoints from interface endpoints. Interface endpoints create network interfaces and have different DNS, security group, availability, and pricing considerations. Replacing one with the other because both contain the word endpoint is not a harmless refactor.

For a private EC2 management design, you may need Systems Manager endpoints, logging endpoints, and other service paths. An S3 gateway endpoint alone does not make Session Manager work. Build the required dependency list from the actual application and operational workflow, then verify the resulting connectivity rather than assuming “private endpoint” covers every AWS API.

4.9 Security groups are stateful allow rules

A security group governs allowed traffic for associated network interfaces or supported resource associations. Rules describe protocol, port ranges, and source or destination scope. Security groups are stateful: return traffic for an allowed tracked connection is handled differently from a stateless packet filter.

Imagine a public load balancer forwarding to private application instances on TCP 8080. A common design allows the load balancer to receive HTTPS from clients, then allows the application to receive 8080 from the load balancer's security group. The application does not need an internet-wide inbound 8080 rule merely because the load balancer serves public requests.

A source security-group reference is not a copy of that group's rules and does not represent every possible route. It identifies a permitted source relationship under AWS's security group semantics. Routing must still carry the packets, and the application must still listen on the expected port.

Prefer narrow, separately owned security group rule resources when that matches the provider's documented approach. Mixing inline and standalone rule management can create ownership conflicts. A complete rule review should state the traffic's purpose, source, destination, protocol, port, and owner. A rule without a known use case is difficult to defend or safely remove.

AWS's security group documentation describes the model and examples. For the lab, we avoid attaching a misleading example group to no workload. The compute discussion supplies realistic relationships when there is a component to protect.

4.10 Network ACLs are a different control

A network ACL operates at the subnet boundary with ordered allow and deny rules. It is stateless, so return traffic needs appropriate rules as well. Rule ordering and ephemeral client ports can therefore matter in ways that differ from security groups.

An organization may use network ACLs as a coarse additional boundary. They are not a convenient substitute for understanding workload-level security group rules. Adding a restrictive ACL before identifying return traffic can break otherwise valid connections and produce confusing symptoms.

The lab leaves the VPC's default ACL behavior in place rather than adding an arbitrary custom ACL whose relationship to a nonexistent workload cannot be meaningfully verified. AWS's network ACL guide is the primary reference for the distinction. In production, inherited ACLs should be inspected as part of the actual network path.

4.11 DNS is necessary for many service connections

DNS maps names to records, including addresses. A network can have correct routes and still fail because a name resolves unexpectedly or not at all. The module enables DNS support and DNS hostnames on the VPC because many ordinary AWS workflows depend on usable naming behavior.

A public DNS name does not necessarily imply a public network path from every caller. Split-horizon DNS, private hosted zones, interface endpoint private DNS, and resolver configuration can change what different clients observe. Diagnose resolution from the actual source environment rather than from your laptop alone.

Terraform data sources can look up hosted zones and other existing DNS objects, but a lookup is a dependency on external ownership. A matching name might not be unique enough, especially across public and private zones. Use explicit identifiers or filters that encode the intended scope, and fail clearly when the lookup does not identify the expected object.

For TLS, names also matter to certificate validation. A reachable IP with a certificate for another hostname is not a successful HTTPS deployment. Later architecture work separates DNS routing, certificate issuance, listener configuration, and application behavior so each can be verified independently.

4.13 Work a connectivity incident from evidence

Suppose a private instance can reach S3 but cannot download software from an internet repository. First observe that the two destinations can use different routes. The S3 gateway endpoint supports one service path. The absence of NAT or another egress design explains the missing general internet path without implying that the S3 endpoint is broken.

Next suppose the S3 request reaches the service but returns AccessDenied. The network path may already be functioning. Inspect the application role, bucket policy, endpoint policy, encryption-key permissions where applicable, and organization constraints. Adding an internet route would not fix an explicit authorization deny and could unnecessarily broaden connectivity.

Now suppose a load balancer returns a gateway error while the instance is healthy when accessed locally. Check listener rules, target port, health-check path, target group membership, application binding address, and security groups between the load balancer and target. Terraform can successfully provision all declared objects even when those application-level values do not agree.

A reliable troubleshooting sequence starts with a specific source, destination name, resolved address, protocol, port, and timestamp. Then trace the route and controls. Avoid “the network is broken” as an initial diagnosis; it is too broad to select a useful next observation.

4.14 Address planning is a compatibility decision

Once clients, peers, and routing systems depend on a subnet range, changing it can require resource replacement and coordinated migration. Treat CIDRs as part of a long-lived interface. A tidy new numbering scheme is rarely worth unplanned replacement of production subnets.

Separate current allocation from future reservation. Our public/private half-space convention is intentionally simple, but it reserves a large portion of the VPC for a small lab. A production plan may allocate by zone, workload tier, or business unit, with explicit growth allowances. Document which dimension the slot represents so future contributors do not reuse it inconsistently.

IPv6 adds another address family and different design considerations. Do not assume that blocking or routing IPv4 traffic also handles IPv6. A dual-stack design needs matching intent across addresses, routes, security controls, DNS, and application listeners. This course teaches the IPv4 baseline thoroughly and treats dual-stack adoption as an expert design extension requiring current service-specific verification.

Consider a hypothetical private application address 10.42.128.20 sending an HTTPS request to an external address. The destination is outside 10.42.0.0/16. In the default lab private route table there is no matching general internet route, so the packet has no intended general egress path. A security-group egress allow cannot manufacture the missing route.

The response would return through the connection mapping. A single rule labeled “allow HTTPS” is only one part of that chain.

Now replace the external destination with an S3 destination covered by the gateway endpoint's service routing. The service-specific path can work without general internet egress. The client still needs DNS resolution and IAM permission. This explains why one AWS request can succeed while an ordinary package download fails from the same host.

For an ALB-to-application connection, identify both endpoints and the return traffic. The load balancer's connection to a target has its own source/destination relationship; it is not literally the original client's TCP connection passing unchanged through every layer. Address arithmetic as an invariant

The tested network module now explicitly limits its input to an IPv4 /16, then adds eight bits for /24 subnets. This restriction makes its teaching contract honest. The public slot range zero through 127 and the private offset of 128 divide the 256 possible /24 slots without overlap when caller slots are unique.

For slot 17, public allocation is 10.42.17.0/24 and private allocation is 10.42.145.0/24. The arithmetic is 128 + 17 = 145. For slot 127, the private slot is 255, the last available /24 slot in this /16. Slot 128 is rejected because its private offset would exceed the chosen range. Those boundary values are more useful checks than trying many arbitrary CIDR strings without a stated invariant.

If you generalize the module later, derive the address policy from the accepted prefix range and validate it. Do not merely remove the /16 validation and leave every downstream assumption unchanged. A more generic interface creates a larger compatibility and testing obligation.

5. Turn infrastructure into an observable HTTP service

Central problem: How do source code, an execution identity, a deployment artifact, an invocation path, and operational evidence become a working service?

Prerequisites: AWS identity and resource dependencies. Chapter 4 supplies the network concepts needed for the EC2 and container comparisons; the runnable serverless lab does not require the VPC lab.

5.1 Separate five responsibilities before choosing a service

A working application needs executable code, a place to run it, an identity for its actions, a way for clients to reach it, and a way for operators to observe failures. Terraform can configure infrastructure for those responsibilities, but declaring a function does not prove its handler returns the response a client expects.

Our reference service answers GET /health with a JSON object containing a status and release identifier. That tiny behavior is deliberate. It is enough to demonstrate artifact packaging, deployment hashing, IAM trust, logging permissions, API integration, routing, and post-deployment verification without adding a database client or framework as an unexplained dependency.

The health response does not certify database availability, cross-region recovery, or every downstream dependency. It demonstrates that a particular invocation path reached a particular release of the handler. Health checks should be designed around their consumers: a load balancer needs to know whether a target can accept traffic, while a deployment probe may also verify the expected release identifier.

We will deploy the small service using Lambda and an API Gateway HTTP API. Then we will compare the corresponding responsibilities in EC2, Auto Scaling, ECS, and EKS. The comparison is architectural; the provided runnable reference does not pretend to implement four full compute platforms.

5.2 Read the complete handler before provisioning it

The function uses only Python's standard library:

import json
import os


def main(event, context):
    method = event.get("requestContext", {}).get("http", {}).get("method", "GET")
    path = event.get("rawPath", "/health")
    if method != "GET" or path != "/health":
        return {"statusCode": 404, "body": json.dumps({"error": "not found"})}
    return {
        "statusCode": 200,
        "headers": {
            "content-type": "application/json",
            "cache-control": "no-store"
        },
        "body": json.dumps({
            "status": "ok",
            "release": os.environ.get("RELEASE", "local")
        })
    }

json.dumps serializes a Python value into a JSON string. The response body is a string because that is what this API integration response contract expects. os.environ reads deployment-provided environment values. The function does not print those environment values or return the entire event, which helps keep the demonstration from exposing incidental request data.

The nested get calls extract the HTTP method from an API Gateway version 2 event while providing a default for simple local calls. The path check rejects unrelated paths if the function is invoked directly with another event. API Gateway also has an explicit health route, so request routing and application behavior reinforce each other.

The configured handler string is handler.main: import the file named handler.py and call its main function. A file placed under an unexpected subdirectory in the ZIP can cause an import error even when Terraform successfully uploads the archive. Artifact layout is part of the executable contract.

5.3 Build an artifact once and identify it by content

An artifact is a deployable package produced from source. Here it is a ZIP containing handler.py at its root. The supplied packaging script uses Python's ZIP library and fixes the archive entry timestamp so unchanged source produces reproducible package bytes in the stated environment.

python ./scripts/package_lambda.py

On systems where Python is invoked as py, use py -3 ./scripts/package_lambda.py. The course already includes a built assets/health.zip, and the readable source remains canonical. Rebuild after changing the handler. Do not edit the ZIP manually and assume the source still represents what will be deployed.

The Terraform function resource uses filebase64sha256(var.package_path) for source_code_hash. This computes a hash from the actual package bytes and encodes it for the provider. When the bytes change, Terraform can plan a code update. A filename alone would not distinguish two different packages written to the same location.

Content identity is a foundation for reliable delivery. Build the package once, test it, retain its digest, and use those bytes during the reviewed deployment. Building a different package between plan and apply can break the connection between the reviewed change and the deployed application. Chapter 10 extends that reasoning to the saved Terraform plan itself.

5.4 The execution role is not the caller permission

Lambda's execution role allows the running function to call other AWS APIs. Its trust policy permits the Lambda service to assume the role. In our module, the attached permissions allow creation of log streams and publication of log events in the explicitly managed log group.

API Gateway's permission to invoke the function is a separate resource policy relationship. The module declares aws_lambda_permission with the API Gateway service principal and a source ARN scoped to the health route. The function's role does not grant API Gateway invocation permission merely because both pieces belong to the same application.

This yields three distinct identities in the workflow: the Terraform executor configures infrastructure, API Gateway invokes the function, and the function's role writes logs. A production data-processing function might also receive table or object permissions, but our health handler does not access those services and therefore receives no such permissions.

The distinction is reinforced by the pinned Lambda resource documentation. When diagnosing AccessDenied, identify which of these identities made the failing request before editing any policy.

5.5 Logging is configured infrastructure

The module creates a CloudWatch log group named for the function and gives it seven-day retention. Without explicit retention, logs can accumulate beyond the intended learning period. A retention period is an operational choice that should reflect investigation needs, privacy, and costs.

The function's log-writing policy references the managed group's ARN with an appropriate stream suffix. That reference establishes a dependency on the log group. An explicit dependency from the function to the role policy expresses the hidden readiness relationship: the function should not be provisioned as ready for use before the required role policy is configured.

Terraform ordering does not eliminate every service propagation delay. IAM changes can take time to become effective across distributed systems. A provider may retry known transient conditions; persistent errors need investigation. Repeatedly adding broad depends_on declarations is not a universal solution to eventual consistency.

Application logs should convey meaningful events without dumping secrets, tokens, or full personal payloads. Our handler deliberately keeps its response and behavior small. For a richer service, choose structured fields such as request ID, operation, outcome, and duration, then define a retention and access policy for the resulting data.

5.6 Trace an HTTP request through the module

The HTTP API defines the public entry point. A route matches GET /health. An integration connects that route to the Lambda function using AWS proxy integration and payload format version 2.0. A default stage deploys the route configuration. The invocation permission allows the matching API source to call the function.

client HTTPS request
  -> HTTP API endpoint
  -> GET /health route
  -> Lambda proxy integration
  -> Lambda invocation permission
  -> handler.main(event, context)
  -> JSON response envelope
  -> client response

The route's authorization type is explicitly NONE. That makes this nonsecret health endpoint publicly callable. It is an intentional demonstration choice, not a recommendation to expose application data routes without authentication. The module returns no customer data and supports only the health path.

5.8 Runtime selection has a lifecycle

The module declares Python 3.13 as the Lambda runtime. The language version used to package a ZIP with a standard-library script is separate from the remote function runtime. For code with native extensions, architecture and operating-system compatibility become additional packaging constraints.

AWS publishes a runtime support schedule. A runtime can enter deprecation stages, and the ability to create or update functions can change accordingly. Review the current runtime documentation before deploying an old course package years later. Pinning a runtime creates clarity; it does not remove the obligation to maintain it.

The reference handler has no third-party Python dependency. If you add a database SDK or web framework, declare and pin the dependency, package it appropriately, and test the resulting artifact. Relying on an incidental library in a managed runtime can undermine reproducibility unless that reliance is deliberate and documented.

A mature deployment records source revision, package digest, runtime, architecture, and environment configuration. Those facts explain what is running more reliably than a folder called latest. They also make rollback decisions more concrete because an earlier release can be identified and reconstructed.

5.9 Capacity is a queueing and limit problem

For a rough steady-state estimate, average concurrent executions are approximately arrival rate multiplied by average execution duration. If a service receives 20 requests per second and each takes 0.2 seconds, the mean in-flight work is roughly four requests. This is a simplified use of the relationship often called Little's Law; bursts, retries, downstream limits, and duration distributions still matter.

Lambda concurrency limits and API throttles constrain different parts of the path. The lab's default stage settings specify a modest rate and burst target to make the demonstration bounded, but throttling is not a hard dollar budget. Requests, retries, and other service usage can still incur charges. Do not advertise the settings as a complete cost-protection mechanism.

The companion's Capacity explorer calculates the approximate in-flight work from arrival rate and duration, then compares it with a chosen concurrency capacity. It labels the calculation as an average model. A value below capacity does not guarantee low tail latency or adequate burst handling.

For real systems, measure latency percentiles, error rates, throttles, and downstream saturation. A function that scales rapidly can overwhelm a database faster than a fixed-size server fleet. Independent service scalability is not the same as end-to-end capacity.

5.10 EC2 teaches a different ownership boundary

EC2 provides virtual machines. You choose an image, instance type, networking, storage, instance profile, and other settings. You also need a strategy for operating-system updates, application installation, process supervision, and replacement. Terraform can provision the machine while an image pipeline or configuration-management process handles the software image.

An Amazon Machine Image, or AMI, is region-specific and has a publisher identity. A lookup that selects the newest matching image can change behavior on a later plan without a source edit. That can be useful for an image-refresh workflow but surprising in a reproducible release. Pin an approved image ID per region or promote a tested image reference deliberately.

User data supplies boot-time initialization instructions to supported images. It is not a reliable secret-delivery mechanism, and it is not a complete ongoing configuration-management system. A script that downloads packages from the internet requires a working egress path; the private network lab intentionally lacks general internet egress.

If you use EC2, prefer role-based credentials through an instance profile and require the appropriate instance metadata protections, including IMDSv2 where supported by your design. Avoid opening SSH to the world as a default lab convenience. Systems Manager can provide administrative access, but it requires a managed agent, permissions, and network paths of its own.

The pinned EC2 instance schema is a reference for supported arguments. The important course lesson is to distinguish a machine's successful creation from the application's successful initialization and readiness.

5.11 Auto Scaling and load balancing turn instances into a service

A launch template describes how to create instances. An Auto Scaling group manages a fleet with minimum, desired, and maximum capacity. A load balancer distributes requests to registered healthy targets. A target group defines the target type, port, protocol, and health check. A listener accepts client traffic and selects a forwarding action.

Trace the dependencies in that order of meaning rather than memorizing a resource list. The launch template needs an approved image and instance security settings. The group needs subnets and a launch template version. The target group needs the VPC and application port. The listener needs a certificate for HTTPS and a forwarding destination. Security groups must permit the client-to-balancer and balancer-to-target paths.

Do not confuse Auto Scaling's desired capacity with a value Terraform must constantly restore. If an autoscaler owns capacity at runtime, define which settings Terraform owns and which are delegated. A narrowly justified lifecycle ignore can prevent ownership conflict, but ignoring all changes would also hide important configuration drift.

Rolling replacement needs spare capacity and a health strategy. “Create before destroy” is not sufficient if account quotas, subnet addresses, unique names, or application compatibility prevent old and new capacity from coexisting. Model the migration path, not only the desired final count.

Launch template user data expects the encoding documented by the provider, which is why a supported expression such as filebase64(...) matters. Exact launch and refresh arguments should be checked against the pinned launch-template schema and related service resources before implementing a production fleet.

5.12 Containers move the package boundary

A container image packages application code and its userspace dependencies under an image format. ECS orchestrates tasks and services; Fargate supplies a managed execution option. A task definition describes containers, resource settings, logging, and execution relationships. An ECS service maintains desired tasks and can integrate with a load balancer.

The task execution role and task role serve different purposes. The execution role supports operations such as pulling an image and delivering logs under the configured platform behavior. The task role supplies the application with permissions for its own AWS calls. Granting the image-pull role application data access can broaden authority unnecessarily.

Pin an image by immutable digest for a reviewed release. A mutable tag such as latest can point to different bytes after a plan, weakening the evidence chain. Terraform should coordinate infrastructure and chosen image identity; it should not become an improvised Docker build script with credentials hidden in local-exec commands.

EKS provides managed Kubernetes control-plane capabilities while leaving additional cluster, workload, identity, networking, and upgrade responsibilities. Terraform is commonly used for clusters and foundational integrations; Kubernetes-native tooling often owns ongoing application deployments. Splitting these concerns can avoid provider initialization cycles and clarify the boundary between infrastructure and workload controllers.

5.14 Diagnose the response path systematically

A missing endpoint can be an output or deployment issue. A 404 can be a route mismatch. A 403 can be an authorization issue or an incorrect request path depending on the API behavior. A 5xx can indicate invocation, handler, dependency, or response-format failure. Use the observed status and logs to select a hypothesis rather than treating every failure as a networking problem.

If the handler cannot be imported, inspect the ZIP root and handler string. If API Gateway cannot invoke the function, inspect the Lambda permission source ARN and integration target. If logs are missing, compare the function name, log group, and execution-role policy. If the response has an old release, compare the deployed environment and artifact against the reviewed inputs.

A good incident record includes the endpoint, timestamp, request method/path, response status, expected release, and relevant request identifiers. Do not include bearer tokens or private payloads merely to make the report look complete. Reproduction steps should preserve the behavior while minimizing sensitive data.

5.15 Optional application with a reference direction

Add a build identifier to the health response through the existing RELEASE environment variable, then verify that a configuration-only update changes the response. Next change the handler's output structure, rebuild the ZIP, and inspect the source-code hash difference in the plan. These are two different deployment mechanisms with different evidence.

A reference solution retains the same function and API identities, changes only the intended environment value or artifact bytes, and verifies the endpoint afterward. It does not create a second function merely because a release identifier changed. If a replacement is proposed, inspect the exact forcing argument before applying.

For a design extension, write the additional controls needed for a private data route: caller authentication, authorization scope, input validation, application data permissions, logging discipline, and tests. The reference module intentionally implements only a public nonsecret health endpoint. Adding a database ARN to an environment variable does not implement CRUD behavior or grant permission to access that database.

Worked readiness distinction: provisioned, reachable, and correct

A function can exist in AWS while its handler fails to import. An HTTP API can exist while its route targets the wrong integration. An endpoint can return 200 while serving the wrong release. These are three different readiness claims, and they need different observations.

Terraform resource success establishes that the provider completed its defined operations and recorded the results it could observe. It does not execute every possible application path. A direct function invocation can help isolate handler behavior from API routing, while an external HTTP request verifies the combined public path. Comparing the release field ties that response to the intended configuration.

If a custom domain is added, introduce another explicit chain: registered DNS name, appropriate certificate validation, API custom-domain configuration, mapping to the intended API/stage, and DNS routing to that target. A valid certificate for the wrong hostname is not a successful deployment. A DNS record pointing at an old API can make the new API healthy but unused.

Keep liveness and readiness semantics deliberate. A liveness check asks whether a process should be restarted. A readiness check asks whether it should receive work. A deployment verification probe asks whether the intended release is serving the expected behavior. Combining every dependency into every check can cause cascading failures: a temporary downstream outage might make an otherwise healthy process restart repeatedly.

For the reference health handler, the promise is intentionally narrow: execute the handler through the configured HTTP route and return the release. A richer readiness endpoint could check a dependency with a bounded timeout, but then its cost, permissions, failure behavior, and information exposure need review. It should not print secret connection details to explain a failure.

Retry behavior changes the application contract

Some event sources retry failed function work. An HTTP caller may also retry after a timeout without knowing whether the first request completed. If a future Field Notes write route creates data, it needs an idempotency strategy appropriate to the operation, such as a client request identifier and conditional write.

Terraform can provision the table, queue, permissions, and retry-related settings, but it cannot make arbitrary application code idempotent. This is another useful ownership boundary. Infrastructure and software contracts meet at the event format, timeout, retry, authorization, and persistence semantics. Expert review follows those relationships rather than assuming a managed compute service removes them.

5.16 Cleanup and the next boundary

Review a destroy plan for the serverless root when finished. It should remove the API, function, role relationships, and managed log group. Logs are evidence with their own retention needs; deleting the group removes the demonstration's operational history. In production, decide whether logging infrastructure belongs to a different ownership and retention boundary.

You now have enough moving pieces that a laptop state file becomes a team concern. If two operators manage the same function from separate state files, both can believe they own it. If a laptop disappears, the configuration alone does not tell the full association history. Chapter 6 turns state storage, locking, access, and recovery into an explicit operational design.

For every compute choice, identify the deployable unit explicitly: a ZIP for this function, an approved image for a VM fleet, or an immutable container image for a container service. Then identify the process that produces and tests it. This simple inventory prevents Terraform from becoming an accidental mixture of artifact builder, secret transporter, application installer, and infrastructure coordinator without anyone reviewing those extra responsibilities.

Part: Ownership and change

Shared state, reusable modules, and deliberate migrations make infrastructure manageable by a team over time. Identity continuity is the connective idea.

6. State as a shared operational system

Central problem: How can a team coordinate ownership, prevent simultaneous writes, protect sensitive values, and recover when state storage or an operation fails?

Prerequisites: the difference between configuration, state, and remote objects; AWS identities, S3, and IAM. This chapter uses the bootstrap root and the module-consumer root.

6.1 Why a configuration file cannot replace state

Suppose the code declares a bucket with a generated name suffix. After creation, Terraform needs to remember which actual bucket belongs to the declaration. The configuration describes intent but does not necessarily contain the final identifier. State preserves that association and other information needed for future operations.

Now imagine two operators each copying the configuration into a new directory with an empty state. Both can plan to create a bucket because neither state associates the declaration with the existing object. Shared code alone does not establish shared ownership. A coordinated backend and a consistent root identity are required.

A backend controls how Terraform stores state and, for supported backends, participates in coordination such as locking. A remote backend is not the same as remote execution. You can run the CLI on your laptop while storing state in S3. A hosted execution platform can run plans and applies elsewhere with additional orchestration and access controls.

State is neither a cache to delete casually nor an editable business document. It may contain sensitive values. Treat its storage, backups, access, and recovery procedures as part of the managed system. The official state overview explains Terraform's need to maintain this information; our operating design builds on that model.

6.2 The coordination problem with two writers

Consider a state snapshot at serial 10. Alice and Ben both read it. Alice adds a logging resource and writes serial 11. Ben, still reasoning from serial 10, adds a monitoring resource. If coordination is absent or bypassed, one write can conflict with the other's assumptions. Even when a storage service rejects a stale write, the team still needs a clear execution sequence and recovery path.

A state lock aims to ensure that only the legitimate lock holder performs a conflicting state operation at a time. A lock is not a data backup. It does not validate the proposed architecture, stop an administrator from changing AWS directly, or coordinate operations against another state file. If two different state keys manage the same bucket, each key's lock can work perfectly while the ownership model remains broken.

The companion's State lock experiment makes these distinctions explicit. Two named clients can acquire, write, and release a modeled lock. A second client is refused while the first holds it, and stale serial writes are rejected by the educational model. The experiment is not an implementation of S3's backend protocol and must not be used as evidence of cloud locking behavior.

Coordination should also exist above the backend. A pipeline concurrency group can serialize a state's apply jobs. The backend lock remains necessary because not every writer will necessarily use the same pipeline. Two complementary controls are useful when they address different ways concurrent operations can arise.

6.3 S3 native locking is the current baseline

The S3 backend supports opt-in lock files through use_lockfile = true. DynamoDB-based backend locking is deprecated in the documentation inspected for this edition. Existing organizations may need a coordinated transition while older clients remain in use; do not remove the old mechanism before every legitimate writer supports the intended new one.

The backend also recommends bucket versioning for recovery. Lock files use a related .tflock object, with permissions that differ from merely reading and writing the state object. These are version-sensitive details checked against the S3 backend reference.

A lock file is not S3 Object Lock. Object Lock is a separate retention/WORM capability with different semantics and can conflict with the deletion behavior a transient Terraform lock requires. Similar names are not evidence of interchangeable behavior.

For a new learning backend, we use a private versioned bucket and S3 native locking. The decision is explicit and narrow. A production backend may also need customer-managed encryption, access logging, organization boundaries, replication strategy, and recovery objectives. Those requirements should be designed around the sensitivity and criticality of the actual state.

6.4 Bootstrap the storage before using it

Terraform must initialize its backend before it can perform ordinary resource operations. It cannot rely on a bucket that will be created later in the same first operation through that backend. This is the bootstrap problem: the storage for managing infrastructure must exist before normal infrastructure management can depend on it.

The course separates a bootstrap root from application roots. labs/04-bootstrap initially uses local state and creates a private bucket through the storage module. That bucket can then hold state for labs/05-modules and other roots. The bootstrap root's own local state must be protected until an independently designed backend migration is performed.

This separation avoids a particularly confusing learning cycle in which a root tries to create, use, and destroy its own backend storage as if all three were ordinary resources in one transaction. Backend configuration has a different initialization lifecycle from provider-managed resources.

Apply the bootstrap root only after setting its verified account ID and reviewing its plan. Record the output bucket name in a protected operational note. The name is not a credential, but it identifies a sensitive system component. The real state and any plan artifacts are not committed to Git.

terraform -chdir=labs/04-bootstrap init
terraform -chdir=labs/04-bootstrap plan -out=bootstrap.tfplan
terraform -chdir=labs/04-bootstrap show bootstrap.tfplan
terraform -chdir=labs/04-bootstrap apply bootstrap.tfplan
terraform -chdir=labs/04-bootstrap output -raw bucket_name

These commands assume the example variables were copied and edited as in earlier labs. The resulting bucket remains empty until a root actually writes state into it. Merely creating it does not automatically redirect other Terraform directories to the backend.

6.5 Configure a root with a partial backend

The course includes a backend block as backend.tf.example so AWS backend access is not required for ordinary local validation. To enable it for the module-consumer root, copy it to backend.tf. Its content is intentionally small:

terraform {
  backend "s3" {}
}

Backend configuration cannot use ordinary input variables, locals, or resource references. It is processed too early for those values. A partial backend lets you provide selected nonsecret settings during initialization through a separate file.

bucket       = "REPLACE_WITH_BOOTSTRAP_OUTPUT"
key          = "sandbox/dev/artifacts.tfstate"
region       = "us-east-1"
encrypt      = true
use_lockfile = true

This is the shape of backend.hcl, not a resource declaration. Replace the bucket placeholder with the actual bootstrap output. The key is the object path for this root's state. It is not the bucket name and not a local directory to create manually.

Credentials should come from the approved environment or profile/role flow rather than being embedded in this file or command history. Backend configuration can be retained in working-directory metadata and related artifacts. Treat “not in a .tf file” as a location change, not a security boundary.

6.6 Migrate existing local state deliberately

If the module-consumer root has already been applied locally, configuring a backend must preserve its existing associations. Freeze other writers first. Preserve a protected copy of the current state and record the expected resource addresses and identifiers. Then initialize with migration:

terraform -chdir=labs/05-modules init -migrate-state -backend-config=backend.hcl
terraform -chdir=labs/05-modules state list
terraform -chdir=labs/05-modules plan

Read every prompt. The command is intended to move state from the old backend to the new one after initialization recognizes the change. If the destination unexpectedly already contains state, stop and investigate ownership rather than accepting an overwrite without understanding both histories.

-reconfigure is a different operation: it tells Terraform to disregard previously saved backend configuration and configure the selected backend. It is not a general synonym for “migrate my state safely.” Choose the option based on whether you need data migration or only a deliberate backend reconfiguration.

After migration, compare the resource list and identifiers, then inspect a normal plan. An unexpected create proposal may mean the wrong state key, workspace, or account was selected. Do not apply a replacement fleet just to make an initialization warning disappear.

The final evidence should show the selected bucket/key, the migration operation, expected associations, and a plausible post-migration plan. It should not publish the state contents. Only after verification should the team resume ordinary writes.

6.7 Scope backend access to the root's needs

For a single default-workspace key, the backend needs bucket listing under appropriate conditions, state-object read/write access, and lock-object access including deletion of the lock file. The precise permissions depend on options such as workspaces and encryption. A customer-managed KMS key introduces its own permissions and key-policy requirements.

The important distinction is between the bucket resource and object resources. A statement granting s3:GetObject on a bucket ARN is not equivalent to granting it on the state's object ARN. Likewise, restricting the state object but allowing unrestricted bucket-wide writes may defeat the intended isolation.

Use separate state prefixes or buckets to reflect real trust boundaries. If the production executor can read every development and shared-services state, then the practical confidentiality boundary is much broader than the folder structure suggests. State readers can often learn sensitive infrastructure attributes even when they cannot modify resources.

A full IAM policy is not pasted here as a universal template because workspace paths, KMS design, account boundaries, and read/write roles materially affect it. The S3 backend documentation lists required operations. Translate those operations into the exact bucket/key model, then verify permitted and forbidden access in the intended environment.

6.8 Backend credentials and provider credentials are independent

The backend accesses state storage. The AWS provider accesses the infrastructure being managed. They may use the same initial environment credentials, but they are configured independently and can assume different roles.

For example, an organization can store state in a tooling account while the provider assumes a deployment role in a workload account. A provider assume_role block does not automatically tell the S3 backend to assume that same role. If initialization fails before provider configuration is evaluated, changing provider arguments may be irrelevant.

This distinction explains a common sequence: init succeeds because the caller can read the state bucket, but plan fails because the provider cannot assume the workload role. The reverse is also possible. Diagnose the caller and target for the failing stage rather than speaking about “Terraform credentials” as if there were only one identity relationship.

A mature run record includes both the backend scope and provider destination. Account allowlists in providers reduce wrong-account mistakes, but they do not prove that the correct backend key was selected. Both must be checked.

6.9 CLI workspaces partition state, not authority

A CLI workspace selects a distinct state instance for the same configuration and backend convention. It can be useful for temporary similar environments. It does not by itself create separate AWS accounts, permissions, approvals, or billing controls.

For the S3 backend, nondefault workspace paths follow a documented prefix/workspace/key scheme. This affects IAM scoping and recovery procedures. A team that assumes every workspace uses the literal key configured for the default workspace can accidentally inspect or restore the wrong object.

Separate root directories with separate backend keys are often clearer when development and production differ in accounts, credentials, lifecycle, and approval requirements. Reusing a module is compatible with keeping those roots distinct. Do not confuse avoiding source duplication with merging operational authority.

HCP Terraform workspaces add platform-specific execution and configuration concepts and should not be treated as identical to CLI workspace switching. The shared word “workspace” has a contextual meaning. Identify which system's workspace is being discussed before following a recovery or automation instruction.

6.10 State outputs can become an accidental data-sharing API

One root may need a value produced by another, such as a VPC ID. Reading a remote state output is convenient, but access to the underlying state storage can expose more than the single output a consumer intends to read. Output-level convenience is not necessarily output-level confidentiality.

For less privileged consumers, publish selected values through a deliberate interface such as a parameter, DNS record, or other service with narrower read permissions. The tradeoff is an additional publication lifecycle and possible propagation delay. Choose it when the trust boundary warrants the extra system.

Outputs are contracts. If a network root publishes a map keyed by logical zone, downstream modules should understand whether those keys are stable. Changing a string output into a differently shaped object can break consumers even when the network resources remain unchanged.

Prefer clear dependencies between roots with explicit promotion order. An infrastructure graph divided across state files is not automatically coordinated by Terraform's single-root dependency engine. The team or orchestration platform must manage cross-root sequencing and compatibility.

6.11 Protect state as sensitive operational data

Setting sensitive = true on an output normally affects presentation. It does not remove the underlying value from state. JSON output and state inspection can expose values that were hidden in ordinary terminal presentation. Saved plans can also contain sensitive information.

Use protected storage, transport security, least-privilege access, short-lived credentials, and careful artifact retention. Keep state and plans out of ordinary source control. A private Git repository is still a poor default state backend because it creates history and distribution semantics that do not match Terraform's coordination needs.

When you inspect state with terraform state show or terraform show -json, consider where the output goes. Terminal transcripts, CI logs, uploaded debugging bundles, and copied screenshots can become secondary data stores. Minimize the scope of the inspection and protect any necessary capture.

The goal is a coherent data-handling design, not a rule that operators may never inspect state. Recovery sometimes requires detailed inspection. Use an authorized role, a protected environment, and an evidence record that avoids unnecessarily redistributing the sensitive payload.

6.12 Recovery begins by stopping uncertainty from spreading

Suppose an apply fails after several resources are created. First stop concurrent writers and preserve diagnostics. Inspect the current state associations and actual AWS objects. A normal subsequent plan often identifies the remaining work because Terraform has recorded successful operations.

Do not restore an old state snapshot merely because the latest apply failed. The old snapshot may omit resources created by the partial apply. Restoring it can make Terraform forget live objects. A backup is a recovery input to reconcile with reality, not an automatic rollback of the world.

If the state object itself is lost or corrupted, use the versioned backend's recovery mechanisms under a documented procedure. Identify the correct bucket/key/workspace, preserve the current object/version if possible, examine candidate snapshots, compare their lineage and serial history, and reconcile them with actual resource identities before resuming writes.

A lineage identifies a state history, while a serial orders snapshots within that history. They help detect incompatible or stale operations. Editing them casually to force a push can bypass useful safeguards. Manual state pushes belong to exceptional, reviewed recovery, not routine troubleshooting.

6.13 Handle a suspected stale lock without creating two writers

A lock can remain after a process crashes or loses connectivity. Before removing it, determine whether the original process is still running, whether another runner owns it, and whether the reported operation is legitimate. Check pipeline status and contact the appropriate operator through your normal team process.

terraform force-unlock exists for recovery, but the name should be taken literally: it can remove the coordination barrier without proving that no writer remains. Removing a live lock can allow conflicting operations. Do not teach force-unlock as the default response to impatience.

If a lock is confirmed stale, record the lock identity and reason, remove it through the supported backend workflow, and run a fresh plan before applying. A previously calculated plan may no longer represent the relevant state after an interrupted operation.

A reasonable timeout while waiting for a legitimate lock can reduce noisy job failures, but it does not solve a permanently blocked writer. Lock duration, run duration, and incident diagnosis are separate concerns. Monitor actual run ownership rather than making the timeout arbitrarily large.

6.14 A recovery rehearsal has measurable outcomes

A useful learning rehearsal uses the local built-in resource lab or a disposable sandbox. Record a known resource ID, preserve state safely, perform an intentional configuration rename with a correct migration, and confirm that the ID remains unchanged. Later, Chapter 8 provides the exact executable procedure.

For a backend drill, choose a nonproduction state and test the documented restore procedure under supervision appropriate to your organization. The evidence should establish that operators can locate versions, select the right state, restore associations, and produce a plausible normal plan. Merely seeing a bucket version in the console does not establish a tested recovery capability.

Define recovery objectives in terms of acceptable lost changes and acceptable time to resume safe management. Those objectives apply to state operations, while the application has its own data recovery objectives. A restored state file does not recover deleted customer records or replay missed messages.

The capstone combines a change rehearsal with an application probe and a data-retention decision. That makes recovery part of the system design rather than an appendix read only during an incident.

6.15 Teardown must respect dependency on the backend

Application roots can be destroyed and their states retained or archived according to policy. Backend storage should outlive the roots that depend on it until their ownership and recovery needs are resolved. Destroying the state bucket first can leave the team unable to manage still-running infrastructure normally.

The bootstrap bucket uses force_destroy = false, so stored state versions can prevent deletion. That resistance is useful. Do not enable automatic destruction merely to make a cleanup command succeed without examining what the bucket contains.

For a complete learning teardown, remove application resources through their own reviewed plans, verify the remaining inventory, preserve any needed evidence, and only then decide whether the backend bucket and all its versions are disposable. The bootstrap root's own state also needs a deliberate disposition. No single universal destroy command understands all those business decisions.

Verify the writer boundary after an incident

After an interrupted run, a successful unlock is only one observation. Confirm the original runner has stopped, establish which snapshot is current, inspect a fresh normal plan, and resume through the usual approved executor. If a second person ran a manual repair, include that action in the reconciliation record before proceeding.

State access should also be reviewed when people or teams change roles. A former deployment operator may retain read authority through a bucket policy, group, or backup location even after a CI permission is removed. Inventory the actual access paths rather than checking only the most visible interface.

For the learning backend, keep the process modest but explicit: one owner, one active state key per root, temporary credentials, native locking, protected versions, and a recorded cleanup decision. Those basics are more valuable than copying an elaborate policy that nobody can explain. As requirements grow, add controls to address the new authority, sensitivity, and recovery needs with corresponding evidence.

A lock timeout should be interpreted with run ownership and timestamps. If the holder is making progress, wait through the normal process. If ownership is unclear, investigate before removing coordination. A faster second writer is not a recovery success if the first writer remains active.

Worked backend review: a state key is a security scope

Assume the tooling bucket contains sandbox/dev/artifacts.tfstate and its companion lock object. A narrowly scoped writer needs the operations documented for the backend on the intended bucket/key, including lock-object deletion for the transient lock. It should not automatically be granted unrestricted object deletion throughout every production prefix in the same bucket.

Write the intended resource scopes before writing policy syntax. The bucket scope is used for relevant listing behavior. The state object scope is the exact state key. The lock scope is the corresponding lock filename. If CLI workspaces are introduced, enumerate their actual prefixed paths rather than assuming the default key remains the only object involved.

Walk through a stale snapshot numerically

Suppose serial 40 records a bucket and a function. An apply at serial 41 adds an alarm, then fails while modifying another resource. The latest state may legitimately include the alarm even though the overall run failed. Restoring serial 40 would remove the alarm association from Terraform's knowledge while the alarm could still exist in AWS.

The correct first investigation compares serial 41's associations with actual objects and the failure diagnostic. If the state is intact, fix the cause and calculate a fresh plan. The next plan can continue from the partial result. The older version is useful evidence of history, not automatically the desired replacement state.

Now suppose the current object is corrupted and serial 40 is the latest readable candidate. Recovery must identify the alarm and any other post-40 objects through surviving diagnostics, inventories, or service records, then reconcile ownership. A state restore without that reconciliation can cause duplicate resources or name collisions on the next apply.

Establish the right recovery permission

The ordinary deployment role and an exceptional recovery role need not have identical authority. Recovery may require reading historical versions or performing a controlled restoration that normal application deployment should not do casually. Separate those powers when the organization's operating model supports it.

A recovery procedure must remain usable under the failure it addresses. If all instructions and credentials are stored only in the broken platform, operators may be blocked. Preserve an approved independent access path and an offline-accessible procedure appropriate to the system's criticality. This does not mean storing secrets in the course or runbook; it means designing the identity recovery path intentionally.

A practical migration acceptance record

After moving a root from local state to S3, record the old and new backend types, intended bucket/key, resource address count, selected important remote IDs, and the observed normal plan. Compare important IDs explicitly. The count alone can remain unchanged while an association points at the wrong object.

Keep the protected pre-migration snapshot until the migration is verified and your retention policy permits disposal. Prevent other writers from using the old local copy as an independent active state. Two valid snapshots are not a problem by themselves; two active authorities managing the same objects are.

Finally, rehearse the return path for an interrupted migration. Determine which storage location contains the latest coherent snapshot before resuming. Do not alternate -reconfigure and -migrate-state options until the CLI stops asking questions. Every initialization choice should follow an understood source and destination history.

6.16 Optional application and transition

Use the companion lock model to walk through two operators attempting to change one state. Then write a short operating note with the root identity, backend location, normal executor, lock ownership check, and recovery contact/process. A reference note identifies a specific bucket/key and account rather than saying “the shared bucket.”

For the real sandbox, migrate labs/05-modules only after a protected local application and state backup. Confirm that a post-migration plan does not propose recreating the bucket. This optional application is successful when identity and the management path are preserved, not merely when initialization prints a success message.

State boundaries now have a clear purpose. The next chapter designs the reusable module boundaries inside and across those roots. It shows how to share architecture without sharing every operational decision or creating an unmaintainable generic wrapper.

7. Reusable modules and independent environments

Central problem: How do we reuse a sound design while preserving clear ownership, reviewable interfaces, and independent deployment boundaries?

Prerequisites: expressions and types, AWS resources, dependency graphs, and state boundaries. The principal example is the private bucket module, consumed by labs/05-modules and the capstone.

7.1 Duplication is a symptom; coupled decisions are the problem

Suppose three teams copy the same bucket configuration. One copy gains versioning, another changes encryption, and the third leaves an old public-access assumption. Copying created independent text, but the organization still expects a common storage policy. A reusable module can express that policy once and give consumers a deliberate interface.

Now imagine a module with 150 inputs mirroring every provider argument, five optional submodules, and Boolean switches for unrelated architectures. It has removed some repeated text while creating a new language that users must learn. The module's value is uncertain because callers still need to understand nearly every provider detail and now need to understand the wrapper too.

A useful module groups resources that form a coherent responsibility and changes for a coherent reason. It exposes meaningful choices, derives routine details internally, and publishes stable results. For this course, a private bucket is a storage contract, a network is an address-and-routing contract, and a health API is a small deployment contract.

Reusability is not the only objective. Reviewability, upgradeability, and failure isolation matter. Two similar roots can legitimately remain separate when they have different owners or operational authority. Sharing a child module does not require sharing state, credentials, or approvals.

7.2 Every module has inputs, internals, and outputs

A root module is the configuration Terraform operates on as its entry point. A child module is called from another module using a module block. Both are directories of Terraform configuration. “Module” does not mean a published registry package; a local folder is a module too.

The private-bucket module accepts a name prefix and tags. Internally it declares the bucket and related controls. It publishes the bucket name and ARN. The consumer does not need to know the internal resource label this to use the module's documented outputs.

module "artifacts" {
  source      = "../../modules/private-bucket"
  name_prefix = "tf-mastery-dev"
  tags = {
    Environment = "dev"
  }
}

output "bucket_name" {
  value = module.artifacts.name
}

This is the core of the supplied consumer root, with provider setup in separate files. source locates the child module relative to the calling module. name_prefix and tags are ordinary input arguments because the child declares variables with those names. module.artifacts.name refers to the child's output, not directly to an AWS resource attribute.

An output should expose a useful contract. Publishing the entire resource object can couple consumers to many provider attributes and future schema changes. Publishing only a name and ARN keeps the interface smaller. If consumers need more, add deliberately named outputs with documented meaning.

7.3 A contract includes behavior, not only type signatures

The storage module's types tell you that a prefix is a string and tags are a map of strings. Its behavioral contract also includes public-access blocking, ownership enforcement, versioning, encryption, TLS enforcement, and resistance to automatic object deletion.

A caller choosing a prefix should not be able to silently disable the module's defining security posture unless that flexibility is an explicit part of the contract. A generic secure = false switch would undermine the module's name and create a branch that needs its own tests and maintenance. If an exceptional storage design is legitimate, a separate module or carefully scoped parameter can be clearer.

Document which behaviors are invariant, which are configurable, and which remain the caller's responsibility. The module does not decide the caller's IAM data-access policy or whether the stored data is appropriate. It does not provide a cross-account backup merely because versioning is enabled. Clear limits make a contract trustworthy.

A module README should include purpose, prerequisites, inputs with defaults and validation, outputs, a complete usage example, security and cost implications, upgrade notes, and test instructions. The deliverable includes those for the course modules so you can inspect the contract from the same perspective as a future consumer.

7.4 Types reduce ambiguity at integration boundaries

The network module accepts a map of zone objects rather than parallel lists of names and slots. This prevents a caller from accidentally supplying three names and two slot values and hoping positional alignment works. The object groups information that belongs together.

The health module accepts a package path rather than a directory to build implicitly. This keeps artifact production outside Terraform's resource graph and lets the caller supply tested bytes. It accepts a release string for visible deployment identity and a context map for selected environment values. That context is nonsecret in the reference design; adding secrets would require a different handling review.

Optional attributes can make a contract easier to adopt while preserving a normalized internal representation. They also introduce default behavior that consumers need to understand. A default is a policy choice. Changing it can alter production even when consumers make no source edit to their module calls.

Avoid any when a meaningful structural type is known. any can be appropriate for a pass-through serialization boundary, but it sacrifices early feedback when used out of convenience. A well-designed type describes the caller's intended decision in the vocabulary of the domain.

7.5 Compose horizontally before nesting deeply

A root can call network, storage, and application modules side by side, then pass outputs between them. This is often easier to understand than a deep chain where the application module silently creates its own network and storage through several wrappers.

Horizontal composition keeps major ownership choices visible at the root. A platform team can supply a network ID to an application module without requiring the application module to create a network. The application module can be tested with explicit inputs and reused in different deployment contexts.

Deep nesting is not automatically wrong. A coherent internal helper can reduce repeated implementation. The concern is whether a reviewer can identify resource ownership, provider destination, inputs, and lifecycle without opening ten layers. If every layer merely renames arguments, nesting may be hiding rather than simplifying the design.

Our capstone composes the artifact bucket and health API at the root and declares the release table explicitly. The Lambda receives the storage identifiers as environment context but does not use them for data operations. That visible limitation is preferable to implying an application dependency that the source does not implement.

7.6 Providers belong to an explicit execution context

Provider requirements declare which provider source and versions a module can use. Provider configurations supply operational settings such as region and assumed role. Reusable child modules should normally declare requirements while receiving their operational provider configuration from the caller.

The root owns the account and region choice. The child module should not silently point itself at a hard-coded account. Terraform's provider-in-modules documentation explains inheritance and explicit mapping.

For a root with an aliased target provider, the module call maps the child's default AWS provider to that configured alias:

module "artifacts" {
  source      = "../../modules/private-bucket"
  providers   = { aws = aws.target }
  name_prefix = "tf-mastery-target"
}

This fragment is part of the complete multi-account root. The alias is a configuration handle, not a second AWS provider plugin version. Two aliases can use different regions or roles while using the same selected provider package.

If a child genuinely needs multiple provider configurations, it declares the appropriate configuration aliases and the caller supplies them. Do not add hidden provider blocks to a reusable child merely to make a one-off example easier. Such legacy-style designs can restrict use with module-level repetition and make removal harder because existing resources retain provider associations.

7.7 Select version constraints for the role of the module

The course pins CLI 1.17.2 and AWS provider 6.0.0 exactly in its runnable examples to make the validated baseline unambiguous. A broadly published child module often uses a compatible minimum/range and documents its tested matrix, while the consuming root chooses a narrower operational baseline and commits its dependency lock file.

Version constraints describe acceptable selections. The provider lock file records a concrete selected package and checksums. The lock file does not pin arbitrary remote module source in the same way. Registry module version arguments and immutable VCS references are separate dependency controls.

For a registry module, choose a reviewed module version. For a Git source, prefer an immutable commit reference where reproducible supply-chain identity is required. A floating branch can deliver different code at a future initialization even if the module call text has not changed. Do not assume that a friendly tag is immutable unless the repository policy enforces that property.

A provider upgrade and a module upgrade can both change a plan. Change one dimension at a time when practical so failures are attributable. Keep an upgrade note explaining the old baseline, new baseline, schema or behavior changes, and evidence from representative consumer configurations.

7.8 Development and production need independent authority

An environment is a set of infrastructure and operating assumptions for a purpose such as development, staging, or production. It is not merely a string inserted into names. Production may need a different AWS account, role, backend key, approval process, retention policy, capacity, and recovery objective.

A clear repository structure can look like this conceptual pattern:

modules/
  private-bucket/
  network/
  health-api/
environments/
  dev/
    backend.tf
    main.tf
  prod/
    backend.tf
    main.tf

This is an architectural pattern, not an extra set of generated runnable roots in the course. The supplied roots demonstrate the components and the capstone shows composition. Create real environment roots when you have their actual account and backend choices.

Repeated small root declarations can be acceptable because they make different authority boundaries explicit. Reuse the coherent child module rather than creating a large conditional root that chooses every production behavior through terraform.workspace checks. A single wrong workspace selection should not be the only barrier between a developer and production.

7.9 Promote a tested definition, not a copied state

Promotion means taking an approved application or module version through environments with environment-appropriate inputs and evidence. It does not mean copying development state into production. State contains object identities tied to the environment it manages.

For a health API release, the promoted unit can include an immutable package digest and a reviewed module/root commit. Development and production use the same intended release identity but different provider destinations, backend keys, and possibly capacity settings. Each environment receives its own plan against its own state.

If you copy state between accounts without a deliberate migration, its resource identifiers and provider associations can point at the wrong objects. Renaming a backend key is a state migration operation, not an ordinary promotion mechanism. Keep code reuse, artifact promotion, and state transfer conceptually separate.

A release record should let an operator answer which source, module version, provider selection, package, and inputs produced a deployment. That information is more useful than a manual note saying “production matches dev.” It also supports comparisons when environments intentionally differ.

7.10 Design optional resources with lifecycle in mind

An optional resource is often represented with count or for_each. Disabling it removes it from the desired instance set and can therefore propose deletion. A Boolean named enable_database is not a harmless display setting when false means destroy the database.

Default values should reflect the safe and useful behavior for the module's purpose, but no default can replace explicit data-retention review. A module that creates storage may need deletion protection or a separate destructive action process. A one-line toggle can carry a large operational consequence.

When optionality changes architecture, separate modules may be clearer. For example, adding a NAT gateway changes routing, addresses, costs, and availability dependencies. Representing it as a casual convenience flag can obscure the magnitude of the choice. If a module supports it, document the graph change and test both branches meaningfully.

A migration from a singleton to a repeated optional instance changes the address form. Use a migration declaration when preserving an existing object. Test the migration with an existing state, not just a fresh empty deployment, because fresh deployments cannot reveal continuity failures.

7.11 Minimize hidden dependencies between modules

A consumer should depend on an output value when that value expresses its real need. If an application needs a subnet ID, pass that ID. Avoid making the entire application module depend on the entire network module unless there is a genuine hidden dependency that cannot be expressed more narrowly.

Broad dependencies can defer data-source reads and make previously known values unknown during planning. That can cause noisy changes or obscure policy content. More ordering is not automatically more correctness; the ordering needs to correspond to a real requirement.

Cross-state dependencies require additional care because Terraform does not automatically plan every related root as one transaction. A network change can break an application state even if the network plan is internally valid. Publish stable interfaces and coordinate incompatible changes through a documented migration.

One useful design is the expand-and-contract pattern: add a new compatible output or resource path, update consumers, verify migration, then remove the old interface later. This spreads a risky synchronized change into reviewable stages. It also requires tracking adoption rather than deleting compatibility code as soon as one consumer upgrades.

7.12 Test a module through its promises

The private-bucket tests use a mocked provider to check selected invariant settings and invalid prefix rejection. They are not intended to retest every AWS feature. A good module test asks whether a supported caller gets the promised shape and whether an unsupported input receives a meaningful failure.

Examples of contract tests include stable output shape, disabled-resource behavior, validation boundaries, and required security settings. Integration tests add real service acceptance and behavior. Upgrade tests use prior state to check that a new module version preserves intended identity or proposes only the documented migration.

A test that merely asserts a string literal equals itself adds little evidence. A test that checks a dangerous branch, such as automatic deletion being disabled, can be useful even if the implementation currently sets a literal, because it protects a meaningful behavioral promise. Explain the promise in the assertion message so future maintainers understand why it exists.

The next chapter's local migration lab is especially valuable for module evolution. It proves that the same managed ID survives an address rename. A test on an empty state would pass even if the module accidentally replaced every existing object during upgrade.

7.13 Write documentation for the next decision-maker

A good usage example is complete in context: it names the provider baseline, declares required inputs, shows a module source, and explains how to initialize, plan, and verify. A code fragment can be concise when it is explicitly labeled and points to the complete runnable root.

Document costs in terms of resource categories and variables rather than freezing an unsupported price estimate. State whether a module creates NAT gateways, load balancers, persistent storage, logs, or public endpoints. A consumer deciding whether to adopt the module needs those facts before application.

Document destroy behavior as carefully as create behavior. Does the module resist deleting nonempty storage? Does it retain logs? Does disabling a flag remove resources? Are there service-level deletion protections? These are interface properties, not incidental details for an appendix.

For a shared module, include a support and ownership expectation appropriate to the organization. A module can be technically reusable while operationally abandoned. Expert platform engineering includes deciding who reviews changes, handles incidents, and communicates deprecations.

7.14 A worked consumer change

Suppose Field Notes needs an additional artifact bucket for staging. The existing root calls the module once for development. A clear approach is to create a separate staging root with its own provider destination and backend, then call the same module with an appropriate prefix and tags.

If the two buckets genuinely belong to one deployment boundary and one owner, a single root can call the module twice or use module-level for_each with stable environment keys. The difference is not syntax. It is whether the resources should be planned, approved, and recovered together.

A reference module-level repetition fragment is:

module "artifacts" {
  for_each    = toset(["dev", "stage"])
  source      = "../../modules/private-bucket"
  name_prefix = "tf-mastery-${each.key}"
  tags        = { Environment = each.key }
}

This fragment requires the ordinary root provider setup. The resulting addresses include module.artifacts["dev"] and module.artifacts["stage"]. Converting an existing singleton call into this form needs an address migration if you want to preserve its current bucket. Do not paste it over a live singleton and assume Terraform infers your intent.

7.15 Recognize abstraction failure from concrete symptoms

If every consumer asks for a new bypass flag, the contract may be too broad or incorrectly grouped. If upgrading the module requires reading all its internals to know what it does, documentation and interface stability may be weak. If a module takes an entire provider resource object as input and returns it unchanged, the abstraction may add little.

If unrelated teams must coordinate every small change because they share one giant root, the state boundary may be too broad. If dozens of tiny states require brittle manual ordering for ordinary work, boundaries may be too narrow. There is no universal module-to-state ratio. Choose boundaries from ownership, lifecycle, risk, and dependency frequency.

Repeated implementation patterns can justify a helper module, but wait until the repeated decision is understood. Premature generic design often encodes guesses that become difficult to remove. A focused module can grow deliberately as real consumers reveal stable requirements.

Use provider documentation as a reference underneath the module. A good abstraction helps users reason about the system; it does not forbid them from understanding the resources it creates. The full source remains included and readable for that reason.

7.16 Optional application and reference direction

Add an output to the storage module that publishes a small object containing the bucket name and ARN. Preserve the existing scalar outputs so current consumers continue to work. Then update one consumer to use the new object and verify that the plan contains no infrastructure changes caused solely by the output addition.

The reference approach treats the new output as an additive interface change. It does not rename internal resources, alter bucket names, or remove prior outputs. If a plan proposes bucket replacement, the implementation changed more than the output contract and should be inspected before application.

For a design exercise, compare one shared root with two independent environment roots. Write the backend key, provider identity, owner, approval path, and recovery procedure for each. The comparison becomes meaningful only when those operational facts are explicit; folder count alone cannot determine the better design.

Worked compatibility review: changing a retention default

Imagine version one of a logging module defaults retention to seven days. Team A explicitly passes seven. Team B omits the input and relies on the default. Version two changes the default to thirty. Both teams upgrade the source version without editing their module arguments.

Team A's effective retention remains seven because its explicit input still wins. Team B's effective retention changes to thirty. The source diff in Team B's root can be a single version string, yet its plan contains a real operational change. This is why defaults belong in the compatibility contract and release notes.

The companion's module experiment computes exactly this distinction. It does not claim that every AWS retention change has the same service behavior; it isolates how the caller interface selects a value. In the real module, plan and service verification establish the downstream result.

A careful release note states the old default, new default, affected callers, reason, cost/retention consequence, and how to preserve the old behavior if supported. A vague note saying “improved logging” does not give consumers enough information to review their plans.

Additive output migration with a concrete shape

Suppose the old module exposes name and arn, and the new preferred interface is an object named bucket. An additive output can be:

output "bucket" {
  value = {
    name = aws_s3_bucket.this.id
    arn  = aws_s3_bucket.this.arn
  }
}

This fragment belongs inside the existing private-bucket module. Keep the old outputs during the supported migration window. A consumer can switch from module.artifacts.name to module.artifacts.bucket.name without altering the bucket declaration. The expected infrastructure effect is none; the interface effect is real and should be tested.

Now imagine changing that object's name field into a nested object without changing its output name. Consumers expecting a string can fail even though the provider resources are unchanged. An output is an API, so version and document its shape deliberately. If an incompatible redesign is needed, introduce a new output or a major-version migration with clear consumer guidance.

Choose a module boundary through a change scenario

Consider a network and database managed by one giant module. The networking team needs to add a subnet, while the database team controls maintenance windows and credentials. If every networking edit requires database access and approval, the abstraction may combine responsibilities that need independent authority.

Splitting them into network and database modules inside the same root improves source organization but does not automatically separate state access or apply authority. Separate roots may be needed for that operating boundary. The split then requires a stable network interface, such as subnet IDs and security-group relationships, plus coordination for incompatible changes.

Conversely, splitting every small resource into its own state can make a routine deployment require many ordered operations and expose fragile intermediate states. The right question is which resources should be reviewed, applied, and recovered together. Let that answer guide state boundaries, then use modules to express coherent reusable implementation within them.

Review a module source before trusting its interface

Inspect provider requirements, variables, outputs, resource types, data sources, provisioners, external programs, and backend assumptions. A polished README can omit a consequential side effect. A source dependency can also change behavior through a floating reference or newly introduced provider.

For an internal module review, trace one caller input to the resource arguments it affects. Trace one output back to the resource value it publishes. Identify the resource addresses that existing consumers depend on. This review is finite and concrete; it is more useful than declaring the module “clean” because its files are short.

When a module uses a public third-party module internally, its compatibility surface includes that dependency too. Pin it appropriately and preserve applicable notices if code is redistributed. Do not claim your wrapper eliminates the need to understand the dependency's lifecycle and security model.

A consumer adoption note that is actually useful

For the private-bucket module, a concise adoption note might say: “Creates a new private versioned bucket with generated name suffix; does not import existing buckets; resists deletion while object versions remain; publishes name and ARN; inherits the caller's AWS provider; requires the course's pinned CLI/provider baseline.” Each clause answers a likely operational question.

For an existing bucket, add a separate adoption/migration plan rather than implying that replacing an inline declaration with a module call will preserve identity automatically. The module's fresh-deployment example and its existing-resource migration are different workflows and deserve different evidence.

Avoid accidental interface promises

Consumers sometimes depend on an internal naming convention even when it was never documented. If a bucket prefix or output key appears in monitoring, scripts, or another root, it has become a practical interface. Inventory those dependencies before reorganizing names.

The remedy is not to promise that internals can never change. Publish the supported interface, migrate legitimate consumers to it, and explain which details remain implementation choices. A small documented contract is easier to maintain than a large collection of accidental dependencies discovered during incidents.

For the course modules, treat the published outputs and explicit behavioral settings as the supported reference contract. Use direct internal addresses only for the tests and migration operations that deliberately need them. This keeps ordinary consumers independent of routine file organization while preserving the ability to inspect source when debugging.

7.17 Transition: a module will eventually need to change

Once a module has real consumers, internal organization becomes a compatibility concern because addresses identify live objects. A rename, extraction into a child module, or shift from count to for_each can require a migration. The next chapter teaches those changes as controlled transitions with observable intermediate evidence, then extends the same reasoning to import, drift, and incident recovery.

8. Change, import, refactor, and recover without losing identity

Central problem: How can we alter a live infrastructure definition while distinguishing intended updates from accidental replacement, ownership changes, drift, and recovery?

Prerequisites: resource addresses, state associations, modules, saved plans, and AWS identity. The fully executable no-cloud migration uses before and after snapshots.

8.1 A final-state description is not a migration plan

A configuration describes a desired result, but there may be several ways to reach it. Updating a tag, replacing a server image, renaming a resource address, and moving an object into another state all have different continuity requirements. A reviewer needs to understand the transition as well as the final design.

Take a production bucket whose Terraform label is poorly named. Renaming the label can be a state-address migration with no AWS change. Changing the actual bucket name generally requires a different remote object. Copying objects between buckets is an application data migration beyond the resource rename. These operations can look like a few edited words while representing very different consequences.

Begin every change by identifying what must remain continuous: remote ID, hostname, data, permissions, service availability, or ownership history. Then inspect which mechanism preserves that property. A no-destroy plan can still change permissions or application behavior, so “zero destroys” is useful evidence but not a universal safety certificate.

The core discipline is to separate address identity, remote object identity, and application continuity. They are related, but no single Terraform feature guarantees all three.

8.2 Read actions at the resource level

A plan can show create, update, delete, replacement, read, no-op, and other operation representations depending on resource kind and CLI version. A replacement combines creation and deletion because a setting cannot be changed on the existing object under the provider's schema or lifecycle rules.

In plan JSON, replacement may have actions such as ["delete", "create"] or ["create", "delete"]. Any policy that checks only for actions exactly equal to ["delete"] can miss replacements. Chapter 9's policy script therefore looks for the presence of delete inside the actions array.

Read why replacement is required. The changed argument may be immutable, an explicit replace request may have been made, or a lifecycle trigger may be involved. The root cause determines whether replacement is intended. Removing a lifecycle trigger without understanding it can merely hide the next symptom.

Computed values can change because a dependency is replaced. Follow the dependency chain far enough to understand the blast radius. A small upstream input can produce many downstream replacements. Conversely, a large textual refactor can preserve every remote identity if addresses are migrated correctly.

8.3 Preserve an address rename with a moved block

The local before snapshot declares terraform_data.old_name. The after snapshot declares terraform_data.new_name and includes:

moved {
  from = terraform_data.old_name
  to   = terraform_data.new_name
}

The block tells Terraform that the object formerly associated with the old address should now be associated with the new one. It does not rename an AWS resource by itself. It supplies an address-history relationship that planning can apply to the current state.

The source and destination must describe a supported move. Moving between unrelated resource types or provider schemas can have constraints that require provider support and current documentation. Do not assume that a moved block converts arbitrary infrastructure objects into other types.

Keep migration declarations long enough for consumers of older module versions to upgrade through the supported history. Removing them too soon can turn a later consumer's upgrade into a destroy/create proposal. A shared module's migration history is part of compatibility, not obsolete clutter simply because the author has already applied it once.

HashiCorp's module refactoring guidance is the primary reference for supported address moves. We use a local built-in resource so the identity effect can be observed directly without cloud risk.

8.4 Execute the no-cloud continuity experiment

Use the before directory as the working root. Do not apply the after directory as an unrelated new state; the point is to change configuration against the same existing state.

terraform -chdir=labs/06-refactor/before init
terraform -chdir=labs/06-refactor/before apply
$taskOriginalId = terraform -chdir=labs/06-refactor/before output -raw identity
Copy-Item ./labs/06-refactor/after/main.tf ./labs/06-refactor/before/main.tf
terraform -chdir=labs/06-refactor/before plan -out=rename.tfplan
terraform -chdir=labs/06-refactor/before show rename.tfplan
terraform -chdir=labs/06-refactor/before apply rename.tfplan
$taskRenamedId = terraform -chdir=labs/06-refactor/before output -raw identity
$taskOriginalId -eq $taskRenamedId

The first interactive apply should create one local resource after you review and approve it. Copying the after configuration changes the address while preserving the state file in the before directory. The next plan should describe a move with no resource recreation. The final comparison should be true.

The course's verification runner performs this experiment in a temporary copy, so the distributed before snapshot remains the original version. If you follow the commands manually, restore the before source from the archive after destroying the local demonstration, or use your own scratch copy from the beginning.

The intermediate evidence is the important part: original ID, move proposal, applied association, unchanged ID, and a subsequent no-change plan. A script returning success without comparing identity would be weaker evidence because it could have silently recreated the record.

8.5 Move a singleton into a module or keyed instance

Extracting resources into a child module changes addresses. A resource that was aws_s3_bucket.notes might become module.storage.aws_s3_bucket.this. Preserving it requires a move from the old address to the new one in the correct module scope.

Changing a singleton module call into for_each similarly changes the address. A migration can associate module.artifacts with module.artifacts["dev"]. The choice of key becomes part of the long-term identity contract. Do not use a secret, a generated ID, or an unstable list position as a supposedly stable environment key.

This is a conceptual fragment for a compatible module-call change:

moved {
  from = module.artifacts
  to   = module.artifacts["dev"]
}

It belongs in the configuration scope containing those module calls. It does not imply that any arbitrary old and new module implementation are compatible. Review the full plan for internal address and argument changes as well.

When converting count-based instances into keyed instances, write the mapping explicitly and verify each existing remote ID. A map such as index zero to api and index one to worker preserves the intended association only if those indices actually represented those services in the current state. Never reconstruct migration mappings from memory when state can provide evidence.

8.6 Import existing objects as a controlled ownership transition

Import associates an existing remote object with a Terraform address. It is useful when adopting infrastructure created manually or by another system. It does not automatically produce a well-designed configuration or guarantee that the object is not already managed elsewhere.

Before importing, identify the remote object, current owner, provider/account/region, and intended Terraform root. Confirm that no other state continues to manage it. Two states managing one object create conflicting authority even if both import operations are syntactically valid.

A declarative import block can look like this illustrative S3 example:

import {
  to = aws_s3_bucket.adopted
  id = "existing-sandbox-bucket-name"
}

resource "aws_s3_bucket" "adopted" {
  bucket        = "existing-sandbox-bucket-name"
  force_destroy = false
}

This is a fragment requiring a configured AWS provider and a real authorized sandbox bucket. Resource-specific import identity formats come from the selected provider documentation. Do not invent an ID format from the resource's display name.

Planning the import lets a reviewer inspect both the association and proposed configuration changes. If the configuration omits meaningful existing settings, the same plan may propose changing them. The goal of an adoption phase is often a faithful no-unintended-change representation first, followed by separately reviewed improvements.

8.7 Generated configuration is a starting observation

Terraform can generate configuration for some import workflows through documented plan options. Generated text reflects schema and observed values, but it does not understand your architecture, ownership boundaries, or desired module interface. It may contain computed-looking details, defaults, or incompatible combinations that need review.

Treat generation as assistance in reconstructing an object description, not permission to apply a large unexplained file. Normalize names, remove unsuitable attributes, preserve required settings, and compare the resulting plan against the current object. Do this in a controlled adoption branch with the correct state and provider destination.

Importing a parent resource does not necessarily import separately managed companion resources. For S3, versioning, encryption, public-access configuration, and policies have their own resource ownership patterns in the provider. Read the resource-specific guidance and plan the complete ownership transition.

The official import overview explains the language workflow. Discovery and generation capabilities continue to evolve; this course's advanced survey distinguishes those from the stable identity principles taught here.

8.8 Stop managing without destroying through an explicit removal

Sometimes an object should remain alive while Terraform relinquishes ownership. Deleting its resource declaration normally proposes destruction, which is not the intended transition. A supported removed block with destruction disabled can express the different intent.

removed {
  from = aws_s3_bucket.adopted

  lifecycle {
    destroy = false
  }
}

This illustrative fragment replaces the corresponding resource declaration in the relevant scope. Review the exact supported address forms and behavior for the selected CLI in the removed block reference. The resulting object remains in AWS and can continue to incur costs.

A removal is an ownership handoff, not cleanup. Record who manages the object afterward. If another state will adopt it, coordinate the sequence so there is neither dual ownership nor an undocumented gap. Preserve identifiers and evidence without copying sensitive state indiscriminately.

Imperative state commands also exist for exceptional operations. Prefer declarative transitions when they make intent reviewable and repeatable. If an imperative operation is necessary, record its exact target and verify a normal plan afterward. The absence of a resource from state list is not evidence that the remote object was deleted.

8.9 Lifecycle rules change transition behavior

create_before_destroy asks Terraform to create a replacement before deleting the old object where feasible. It can support continuity when both versions may coexist. It cannot override unique-name constraints, account quotas, subnet exhaustion, application incompatibility, or external service limits.

prevent_destroy rejects certain plans that would destroy the protected configured resource. It is a useful guardrail but not a complete backup or organizational access control. Removing the resource block also removes the configured rule, so do not rely on it as protection against every possible deletion path. AWS service-level deletion protection can provide a separate layer where supported.

ignore_changes delegates management of selected attributes after creation under its documented semantics. It can be appropriate when an autoscaler owns a desired count. It can also conceal important drift if applied broadly. Document the external owner and why ignoring that attribute is correct.

replace_triggered_by can make replacement follow another managed change. Use it for a real lifecycle relationship, not as a vague “refresh everything” mechanism. Lifecycle rules are interpreted during graph construction, so their expression capabilities differ from ordinary resource arguments. Check the lifecycle reference for the selected version.

8.10 Preconditions, postconditions, and checks have different force

A precondition expresses an assumption that must hold before the relevant operation proceeds. A postcondition verifies a condition about a resulting value. They can make domain constraints visible near the resource or data they protect. Use error messages that explain the violated assumption without exposing secrets.

A check block is intended for ongoing validation-style observations and reports failures differently from a hard blocking precondition. Do not assume every failed check automatically stops an apply. Choose the construct based on the required enforcement behavior, then test that behavior under the pinned CLI.

Conditions can depend on unknown values, so their evaluation may be deferred. A reviewer should know which assertions are established during planning and which can only be checked after application. An assertion that cannot be evaluated until after a destructive operation is not a substitute for pre-change risk review.

For example, a network module can reject duplicate address slots before resource creation. An application readiness check needs an actual endpoint and may run after deployment. Both are useful, but they protect different stages of the workflow.

8.11 Drift is an observed difference, not automatically an error

Drift occurs when actual infrastructure differs from the configuration/state expectations used by Terraform. A console edit, external controller, service default, or emergency response can cause it. The correct response depends on whether the external change is legitimate and who should own the setting.

A normal plan refreshes relevant observations unless options alter that behavior, then proposes reconciliation toward the configuration. A refresh-only plan proposes recording observed remote changes in state without the ordinary configuration-driven infrastructure reconciliation. Applying refresh-only does not update the configuration text to match the world.

If an operator intentionally increased capacity during an incident, choose whether to adopt that change into code or restore the declared setting. Do not blindly apply the old configuration just to make a drift alert green. The incident may have exposed a real capacity requirement.

If an external controller legitimately owns an attribute, establish a documented delegation rather than fighting it on every apply. Conversely, do not use ignore_changes to conceal an unauthorized security change. Ownership and intent determine the remedy.

8.12 Targeted operations are exceptional tools

The -target option narrows selected operations and their dependencies. It can assist recovery or unusual workflows, but routine targeted applies can leave the overall configuration only partially reconciled. They weaken the assumption that a completed run represents the root's full desired state.

Use an ordinary plan after a targeted operation to reveal remaining changes. Record why targeting was necessary and what was excluded. A pipeline that always targets one convenient resource may be encoding a root boundary problem rather than a sustainable deployment model.

Similarly, -refresh=false can reduce observation work in particular circumstances but can produce plans based on stale information. Disabling refresh to remove an inconvenient difference does not resolve the underlying ownership or drift issue. Understand which evidence you are choosing to omit.

An explicit -replace=ADDRESS request can ask for replacement of a managed resource without relying on the older taint workflow. Review the resulting plan and replacement effects. A replace request is an instruction with operational consequences, not a repair spell that makes any failed application healthy.

8.13 Rollback is often a forward change

Reverting a Git commit changes configuration text. It does not guarantee that the previous infrastructure state can be restored safely. A database engine downgrade may be unsupported, a deleted bucket's contents may be gone, or an older provider may not read a state schema written by a newer provider.

For application artifacts, rollback may mean redeploying an earlier immutable package. For infrastructure, recovery may require a new forward change that restores a compatible setting or creates replacement capacity. For data, it may require restoring a backup and reconciling writes. Keep these recovery planes separate.

Before a risky migration, define the point at which reversal becomes difficult. For a schema expansion, old and new application versions may coexist until a later contraction. For a storage migration, dual-read or controlled cutover may be necessary. Terraform can manage supporting resources, but it does not automatically implement the application data movement.

A plan review should include the recovery path and the evidence required to decide whether to continue. “We can revert the PR” is insufficient when the remote operation is irreversible or the old software cannot interpret the new state.

8.14 Work a partial apply incident

Imagine a plan creates an IAM role, a log group, and a function. The role and group succeed, but the function fails because the package's handler path is wrong. First preserve the error and current state. The successful resources may already be recorded, so deleting state or restoring a pre-apply snapshot can make the situation worse.

Fix the artifact layout or handler configuration, rebuild if needed, and calculate a fresh normal plan. The expected next proposal should focus on the remaining or corrected function-related work while preserving already-created identities. If it proposes recreating the role and log group unexpectedly, inspect the backend, workspace, and current associations.

After the apply succeeds, invoke the health endpoint and inspect the release. A successful resource operation is not enough to close an application incident. Capture the new evidence and remove obsolete plan artifacts through the normal retention process.

For a destructive data incident, the workflow differs: stop additional harm, preserve relevant versions and logs, establish the last good data state, restore into an appropriate target, and validate before cutover. Terraform state recovery alone cannot recreate deleted object contents without the underlying storage recovery mechanisms.

8.15 Make change review readable to another engineer

A good change description names the concrete trigger, before-and-after behavior, preserved identities, intentional replacements, test evidence, and material limits. It need not narrate every command. It should let a reviewer connect the source diff to the plan and the operating objective.

For the local rename, a concise description is: “Rename the managed release record address while preserving its ID through a moved block. The migration plan shows no resource recreation, and the before/after ID comparison passes.” For a production database change, substantially more evidence would be appropriate.

Separate routine generated noise from meaningful differences during your analysis, but do not hide unknowns or replacements in the deliverable. If a provider upgrade changes many computed fields, explain which differences are expected and how you established that. Reviewers cannot approve what they cannot connect to a known mechanism.

Retain migration evidence for the supported consumer window. Shared modules need a versioned compatibility story so a user upgrading from an older release can follow a supported path. Technical correctness on the author's current state is only one consumer case.

8.16 Optional application and reference approach

In a scratch copy of the local lab, change the greeting record from a singleton into a for_each map with key primary. Add the appropriate moved block, plan against the existing state, and verify the original ID survives. The reference direction maps the old singleton address to the new keyed address and keeps its input unchanged during the identity migration.

Then make a separate input change. Separating the rename from the behavior change makes the evidence easier to interpret. If the first plan preserves identity and the second updates only the intended value, you have demonstrated two independent mechanisms rather than hoping a combined diff behaved as intended.

In the companion's Migration planner, compare a rename with and without an explicit move mapping. Its output computes continuity from the modeled address relationships and flags deletion/recreation when ownership is not preserved. Worked handoff: moving ownership between two states

A move inside one state and a handoff between states are different operations. A moved block changes addresses within the supported configuration/state context; it is not a general cross-backend transaction. If a platform team transfers a bucket to an application team's state, both sides need a coordinated ownership procedure.

Begin by freezing writers to the affected object. Record its exact remote identity, current owner/state, destination provider/account, and intended destination address. Preserve protected snapshots. The source owner must relinquish management without destroying the object, and the destination must adopt it without creating a duplicate or changing settings unintentionally.

Separate data migration from resource ownership

Suppose the destination architecture requires a differently named bucket. Importing the old bucket under a new Terraform label does not rename the bucket. The same principle applies to databases. A new endpoint and a copied snapshot do not necessarily preserve in-flight writes or client behavior. A schema migration can need application compatibility across old and new versions. The infrastructure plan must be integrated with the data and application transition.

Maintenance windows create a fourth state to observe

For some services, a requested update is accepted but pending a maintenance window. There is then a distinction among desired configuration, recorded Terraform information, current service behavior, and pending service modification. Repeated plans can reflect this transition without indicating a broken provider.

Inspect the service's actual pending changes and the provider's documented update semantics. Decide whether waiting, scheduling, or an immediate-apply change is appropriate. Forcing replacement just to eliminate a temporary diff can produce unnecessary downtime and data risk.

A stop condition is part of the migration design

Before a risky transition, define observations that require stopping: an unexpected replacement, a mismatched account, missing backup evidence, an unrecognized current owner, a changed remote ID, or an application probe that reports the wrong release. A stop condition should trigger a specific next investigation rather than a vague instruction to be careful.

Also define the resume evidence. For example, after resolving a package error, require a fresh plan against the current state and a successful local handler check. After resolving ownership ambiguity, require both state owners to agree on the handoff and verify the exact object ID. This makes recovery purposeful and prevents repeated trial-and-error applies.

Compare observed identity after the transition

A migration review should not stop at the plan. Record the important IDs again after application and compare them with the intended continuity claims. If an object was intentionally replaced, verify the new identifier and the old object's disposition. If it was only moved, verify the original identifier remains associated with the new address.

Then check the application-facing property separately: endpoint, release, permitted access, or data availability. Identity continuity is valuable, but an unchanged ID can still contain a harmful configuration update. Conversely, an intentionally new ID can be part of a successful blue/green migration if traffic and data continuity were designed correctly.

The smallest sufficient evidence depends on the promise. For the local record, an ID comparison and normal plan are enough. For a database cutover, connection behavior, data validation, and recovery readiness need their own observations. Scale the evidence to the actual transition.

9. Testing, policy, and security as different kinds of evidence

Central problem: How can we catch meaningful mistakes before deployment without confusing a formatting pass, a mocked result, a policy decision, and a real service test?

Prerequisites: resource contracts, plans, identity, state sensitivity, and migration behavior. The course includes Terraform tests under each module, a plan policy checker, and local verification scripts.

9.1 Begin with a claim, then choose the evidence

“Tested” is too vague to guide an infrastructure decision. A formatting check establishes consistent presentation. A validation check establishes selected structural and schema relationships. A mocked test can establish a module's response to controlled provider values. An integration test can establish service acceptance and selected real behavior. A production probe can establish a narrow observation at a particular time.

Start by writing the claim. For example: “The network assigns slot zero in the private half to 10.42.128.0/24.” A mocked Terraform plan can check that expression and configuration relationship. The claim “a private workload can retrieve a specific S3 object through the endpoint” requires a real workload, network path, IAM identity, and object. The first test cannot establish the second claim.

Likewise, “no resource deletion is present in this plan” is a policy-checkable property of the action list. “This change cannot cause an outage” is far broader and cannot be inferred from the absence of delete actions. An in-place security group update can interrupt traffic, and a code update can break application behavior without deleting infrastructure.

The purpose of a layered evidence strategy is to catch errors close to where they become observable and communicate what uncertainty remains. It is not to produce the largest possible number of green badges.

9.2 Put checks in an economical order

Run cheap local checks before expensive external work. A practical sequence is formatting, initialization with the intended dependency selection, validation, local/mock contract tests, plan, policy review, human approval where required, apply, and post-deployment probes.

Initialization is part of the dependency workflow and can access networks. Keep the provider lock file committed and use read-only lock behavior in controlled pipelines where appropriate. A test job that silently upgrades dependencies is testing a moving target.

terraform fmt -check -recursive
terraform -chdir=modules/private-bucket init -backend=false
terraform -chdir=modules/private-bucket validate
terraform -chdir=modules/private-bucket test

Run formatting from the course root so the recursive scope is clear. -backend=false skips backend initialization for module testing; it is not a guarantee that every subsequent operation avoids AWS. The mocked provider in the test file is what prevents its AWS resources from being created.

Tests should be proportionate to the change. A reversible wording correction does not need a cloud integration environment. A module migration that changes addresses needs existing-state evidence. Repeating a broad test suite after no relevant change can consume time without reducing the uncertainty that matters.

9.3 Understand Terraform's test execution model

Terraform discovers files with the .tftest.hcl or supported JSON test extension. A file contains run blocks and optional variables/provider configurations. A run normally applies unless command = plan is selected. Tests can create real resources and incur charges.

The course makes command mode explicit in its tests. The local service-manifest tests use apply against the built-in terraform_data resource, which has no AWS effects. The AWS module tests use a mocked AWS provider and plan-based assertions. These are different reasons for avoiding real cloud deployment.

mock_provider "aws" {
  mock_data "aws_iam_policy_document" {
    defaults = {
      json = "{\"Version\":\"2012-10-17\",\"Statement\":[]}"
    }
  }
}

variables {
  name_prefix = "tf-mastery-test"
}

run "bucket_contract" {
  command = plan

  assert {
    condition = (
      aws_s3_bucket.this.force_destroy == false &&
      aws_s3_bucket_public_access_block.this.block_public_policy
    )
    error_message = "Preserve deletion resistance and public-policy blocking."
  }
}

This excerpt demonstrates the test's structure; the canonical test file includes the full assertions. The mock policy-document default is syntactically valid JSON for consumers that validate JSON. It is not a useful real trust policy, and the test does not claim that AWS would accept it for every role.

HashiCorp's test language reference and mocking reference define the version-sensitive execution behavior. The distinction between apply and plan must be understood before running unfamiliar test repositories.

9.4 Mocks should model the boundary you need

A mocked provider supplies computed values without calling the real service. Automatically generated placeholder strings are convenient, but downstream configuration may impose structure. An ARN-shaped value, a JSON policy, or a region name may need an explicit default so the test evaluates the intended relationship rather than failing on unrelated placeholder syntax.

During authoring, the health module's first mock run failed because the generated trust-policy value was not a JSON object. The correction supplied a valid JSON-shaped mock at the data-source boundary. That failure was useful: it showed why a mock is a controlled input, not an oracle that automatically understands every downstream semantic requirement.

Do not overfit mocks so every test passes regardless of implementation. If an output depends on a resource association, choose mock values that make the association distinguishable. If two resources receive identical fake IDs, a wiring error can become invisible.

Document the mock's omissions. Our health contract test checks configured timeout, memory, route path, and public-health intent. It does not verify IAM propagation, actual invocation, API response serialization, or runtime availability. Those belong to other checks.

9.5 Test invalid inputs as deliberate behavior

A module contract includes failure behavior. The storage module rejects an invalid prefix. The network module rejects duplicate slots. The local module rejects an unknown environment label. Tests can declare the expected validation failure rather than treating it as a broken test run.

run "reject_bad_name" {
  command = plan

  variables {
    name_prefix = "INVALID NAME"
  }

  expect_failures = [var.name_prefix]
}

This run is successful when the declared validation failure occurs as expected. It does not mean every diagnostic is acceptable. The expectation should identify the intended condition, and unrelated errors must still be investigated.

Boundary cases are valuable when they exercise the domain: duplicate address slots, a negative replica count, an empty required collection, or an unsupported environment. A large random collection of arbitrary strings is less useful if it does not correspond to a meaningful failure mode.

Avoid imposing mandatory quizzes on yourself as a substitute for implementation evidence. The optional applications in this course let you extend the system and compare a reference direction. Automated checks focus on concrete promises the code makes.

9.6 Integration tests need their own lifecycle

A real integration test needs an isolated account or sufficiently isolated resource scope, a bounded identity, unique names, cost expectations, cleanup logic, and evidence of what remains after failure. If cleanup fails, the test runner should surface the remaining resources rather than claiming the test environment vanished.

Do not run a repository's default tests with production credentials merely because the files are called tests. Inspect resource types, provider configurations, run commands, and setup scripts first. The same Terraform engine used for deployment can create meaningful infrastructure during a test.

For the health API, an integration test can deploy a uniquely named sandbox service, call the endpoint, assert status and release, inspect relevant logs, and destroy the environment through a reviewed workflow. That would establish a real end-to-end path for the tested account and region. It would not establish every browser, region, concurrency condition, or failure mode.

The course was authored without deploying to your AWS account. Its verification report distinguishes executed local/mock tests from the provided instructions for real integration. That honesty is part of the engineering standard being taught.

9.7 Parse plans as structured data

Terraform can render a saved plan as JSON:

terraform -chdir=labs/00-local plan -out=review.tfplan
terraform -chdir=labs/00-local show -json review.tfplan |
  Set-Content -LiteralPath ./review-plan.json -Encoding utf8
python ./scripts/check_plan.py ./review-plan.json

The output path for Set-Content is relative to the shell's current directory, while the plan path in the Terraform command is relative to the selected module. This is why the example writes the JSON file explicitly in the course root. Inspect paths carefully when moving commands into scripts.

Plan JSON can contain sensitive values, including values hidden in normal CLI presentation. Protect it like a plan artifact and do not upload it indiscriminately to an external “analysis” website. The show command reference documents its output modes and sensitivity implications.

A policy should parse the schema rather than search the raw JSON text for words such as delete. A harmless description might contain that word, while a replacement's action array might be missed by a simplistic exact match. Structured data lets the checker reason about the actual field.

9.8 Walk through the included policy checker

The included Python checker reads one plan JSON file and returns a process exit code. It rejects invalid or unsupported input, flags delete actions unless an explicit address allowance is supplied, flags automatic S3 object deletion, and flags public-access-block resources whose required settings are not known true.

The algorithm begins with the plan's resource_changes array. For each entry, it reads the address, resource type, action list, planned after-values, and unknown-value markers. If the actions contain delete, the change needs the explicit deletion allowance. That catches both deletion-only actions and replacement combinations.

For a planned public-access-block resource, the checker requires the four expected blocking flags to be true. A missing or unknown flag is not silently treated as safe. This is a narrow fail-closed rule for a property whose safe value the policy knows. It does not mean every unknown value in every resource should be rejected globally.

The checker intentionally does not implement the entire AWS authorization model, prove application availability, or scan every possible public-exposure path. It is a teaching-quality executable policy with a documented scope. Extend it only when you can specify the rule's meaning, legitimate exceptions, and test fixtures.

A policy exception should identify the exact resource address and reason through the surrounding review process. A broad “skip security” switch would erase the distinction the policy is intended to protect. The script prints addresses and reasons rather than dumping resource values, reducing unnecessary sensitive output.

9.9 Test the policy's dangerous cases

The supplied unit tests use synthetic plan fragments. They cover a harmless create, deletion, replacement in both action orders, an explicit address exception, unsafe bucket destruction, unknown/missing public-access settings, malformed input, and a declared incomplete plan. These cases target the places a naive checker would plausibly fail.

Run the tests with Python's standard unittest runner:

python -m unittest discover -s ./scripts/tests -v

A fixture is not a captured private account plan. Synthetic minimal cases make the policy logic reviewable and portable. The verification workflow also runs the checker against a real locally generated Terraform plan so the parser is exercised on actual CLI output.

A passing policy result means only that the encoded rules passed on the supplied plan representation. It is one input to approval. Human review still needs to consider account, environment, application semantics, costs, data retention, and the recovery path.

9.10 Secrets have a dataflow, not just a label

A secret can enter through a variable, environment, data source, or generated value. It can then flow into resource arguments, state, plans, logs, outputs, artifacts, and application configuration. Security review should follow the value through that path.

sensitive = true marks a value for restricted normal display. It does not generally prevent persistence in state or saved plans. Terraform's newer ephemeral values and provider write-only arguments offer different persistence semantics in supported contexts, but support depends on CLI and provider/resource schema.

For example, the following is an illustrative variable declaration, not a complete database deployment:

variable "database_password" {
  type      = string
  sensitive = true
  ephemeral = true
}

An ephemeral value cannot be inserted into arbitrary persisted attributes. It must flow through contexts that support ephemeral use, such as a compatible write-only argument. Marking an input ephemeral does not magically make a normal password argument nonpersistent. Check the exact provider resource schema.

HashiCorp's sensitive-data guidance distinguishes presentation, ephemeral values, and write-only support. The pinned RDS schema includes write-only password capabilities, but the course does not deploy a database merely to demonstrate the syntax.

9.11 Prefer not handling a secret when the service can manage it

Some AWS services can generate and manage credentials through an integrated secret-management path. For RDS, a managed master-password design can avoid supplying a plaintext password through ordinary Terraform inputs. It still creates an access and key-management system that needs review.

A secret stored in Secrets Manager can still enter Terraform state if a normal data source reads its secret value and passes it into a persisted argument. Moving the storage location is not the same as changing the infrastructure tool's dataflow. If the application can retrieve the secret at runtime through its role, Terraform may need only to configure the secret reference and permissions.

Environment variables are convenient configuration but not a universal secret boundary. Users with relevant management permissions can often inspect them, and application logging can expose them. Choose a delivery mechanism based on who may read the value, when it must be available, and which systems retain it.

Rotate secrets through a deliberate service/application process. Terraform resource replacement is not automatically a correct rotation protocol. A database credential change can require coordinated client updates, overlap, and verification to avoid an outage.

9.12 Supply-chain trust applies to infrastructure tooling

Terraform providers are executable plugins. Modules are code that can influence infrastructure and, through provisioners or external integrations, may execute additional commands. A registry hostname or popularity score is not proof that a dependency is appropriate for your environment.

Review provider source identity, version, checksums, release provenance, and compatibility. Commit the dependency lock file. For modules, pin reviewed versions or immutable references and inspect meaningful changes. Keep dependency upgrades in a workflow with representative plans and tests.

The course uses the official HashiCorp AWS provider at a fixed version and includes its lock records. The validation environment initially obtained the provider through the registry's signed package path, then reused that known package locally. The final package does not distribute provider binaries, credentials, or plugin caches.

Be cautious with provisioners and external data sources. They can cross from declarative infrastructure into arbitrary process execution. When they are necessary, document input trust, idempotence, failure behavior, secrets handling, and the verification path. Prefer purpose-built resources and external build pipelines when those provide a clearer ownership model.

9.13 Static scanners complement, rather than replace, design

Tools such as infrastructure linters, security scanners, and policy engines can identify known configuration patterns. Their usefulness depends on maintained rules, selected versions, appropriate exceptions, and clear integration into review. A scanner cannot infer every business requirement from a resource block.

This course provides an executable small policy checker rather than assuming a particular commercial scanner is installed. For a production tool choice, consult current primary project documentation and evaluate language/provider support, rule transparency, integration, and maintenance. Do not install arbitrary plugins solely because a course mentions the category.

Policy as code platforms such as OPA or Sentinel can express organization-wide rules and integrate with execution systems. The same design questions apply: what claim does a rule make, what input schema does it consume, how are unknown values handled, and who can approve a scoped exception?

A rule that rejects all changes may be safe in a narrow sense but unusable. A rule that allows everything is easy to operate but meaningless. Effective policy encodes a real boundary with a supportable exception process and tests for its likely failure modes.

9.14 Security review across the actual architecture

For the health service, review the public endpoint's intentionally limited behavior, the Lambda invocation scope, the execution role's logging-only permissions, artifact identity, runtime, log retention, and absence of secret output. For the bucket, review public access, ownership, encryption, TLS, data retention, and authorized readers.

For the network, review routes and workload security relationships separately from IAM. A private subnet is not proof of data confidentiality. For the backend, review who can read state, who can write it, who can remove locks, how versions are recovered, and how identities are audited.

For CI, review who can modify the workflow and source that receives credentials. A narrowly scoped cloud role does not help if an untrusted pull request can alter a job that assumes that role and then execute arbitrary commands. The trust boundary includes the repository and runner, not only AWS.

Threat modeling can remain practical: identify the valuable data or authority, the legitimate actors, plausible entry paths, and the controls that restrict those paths. Then choose tests that demonstrate the relevant control rather than relying on a generic label such as “private” or “encrypted.”

Worked test design: prove one property at each boundary

A real integration check can verify AWS accepted the chosen zones and created the intended route associations. A workload test can verify a permitted S3 request from an actual private client. These are four distinct claims with increasing external requirements.

Define the plan policy's trust boundary

The checker consumes a JSON representation produced by the selected Terraform CLI. It assumes that the caller supplies the intended saved plan and protects it from replacement. It cannot establish that relationship merely by reading a filename. The delivery pipeline adds digest consistency, while the runner/artifact system must supply authorization and provenance.

The checker also assumes that its rule set is the intended policy. A contributor who can change the policy script in a privileged job may be able to weaken the rule before running it. Protect policy changes through the same review and authority model as deployment workflow changes. A policy file is executable governance, not neutral documentation.

Exceptions should remain visible. If a resource deletion is legitimate, record the exact address and the surrounding approved reason. An allowance for one address should not permit another resource's deletion. The unit tests include this distinction because exception broadening is a plausible implementation mistake.

Allowing every unknown would let an unenforceable required security property pass. The policy must distinguish between unknown values that are expected identifiers and unknown values whose known safe setting is required for the rule.

For public-access blocking, the desired booleans should be explicit in configuration, so requiring known true is reasonable. For a provider-generated bucket suffix, unknown is normal and does not indicate unsafe exposure. This is why the checker targets named properties instead of treating the entire plan as a flat collection of strings.

If the input plan declares itself incomplete or errored, the educational checker rejects it. A production policy engine may have richer staged-plan semantics, but those need deliberate support. Failing closed on an unsupported schema or action prevents the parser from silently treating a new representation as safe.

Verify the tests can detect the intended regression

A meaningful test suite should fail when the protected behavior is intentionally broken in a temporary working copy. For example, change force-destroy to true and observe the contract or policy failure; restore it afterward. This is a targeted mutation check, not a requirement to build an elaborate mutation-testing platform for every small change.

Similarly, a replacement fixture should fail regardless of action order. A malformed plan should produce an input error rather than a success. A handler test should detect an incorrect release value rather than merely checking that a dictionary exists. These examples keep test maintenance tied to plausible mistakes.

Do not leave deliberate broken mutations in the final source or package. Rebuild verification outputs from the restored canonical source so the evidence corresponds to the delivered edition.

Keep evidence aligned with the delivered revision

When a check finds a real defect, fix the canonical source and rerun the affected checks before packaging. A report from an older revision is historical evidence, not proof about the current one. The same applies when a generated artifact is rebuilt after source changes.

Record enough version information to reproduce the relevant result: CLI/provider selection for Terraform, runtime for the handler, and model source for companion calculations. Avoid collecting unrelated machine details that add noise without explaining behavior.

A useful verification report separates local execution, mocked execution, structural inspection, browser interaction, and unexecuted cloud integration. Readers can then decide what additional evidence their environment requires. This is more actionable than an unqualified statement that everything works, and it makes future maintenance easier because each claim has an identifiable check.

Checks become most useful when they run on the same source, dependencies, inputs, and artifacts that will be deployed. 10. Deliver the change that was actually reviewed

Central problem: How do we connect source review, dependency selection, a saved plan, authorization, execution, and post-deployment evidence without letting untrusted code inherit deployment authority?

Prerequisites: state locking, module contracts, plan JSON, policy checks, and artifact identity. The complete portable implementation is scripts/pipeline.py. It runs locally or inside a CI runner that already has the declared tools and approved credentials.

10.1 CI and delivery are a chain of trust

Continuous integration runs checks when code changes. Delivery turns an approved change into an operational system. Infrastructure delivery is especially sensitive because the code under review can alter identities, network paths, data stores, and the machinery that performs future changes.

A trustworthy chain connects a specific source revision to selected dependencies, explicit inputs, built application artifacts, a plan, policy results, approval, an executor identity, and observed results. If one link changes without another review, the final deployment may no longer correspond to what was approved.

For example, a reviewer can approve a plan for release A while the apply job downloads a mutable latest package that now points at release B. The Terraform source diff may look unchanged, but the deployed bytes differ. Likewise, approving a speculative plan and later running an unconstrained terraform apply calculates a new plan rather than necessarily executing the reviewed proposal.

The objective is not to make plans live forever. It is to ensure a short-lived reviewed proposal is executed in the intended context, with fresh replanning when relevant facts change. Automation should reduce ambiguity, not hide it behind a green pipeline icon.

10.2 Teach the Git prerequisite explicitly

Git records snapshots of files and the relationships among those snapshots. A commit identifies a source state. A branch names a moving line of development. A pull request or merge request proposes integrating changes and provides a place for review. None of these automatically runs Terraform or grants cloud permissions.

For a course folder you choose to maintain in your own repository, initialize Git, review the ignore rules, add intended source files, and make an initial commit. Keep state, local variable files, saved plans, credentials, and dependency caches out of that commit. Check what is staged before committing.

A source diff is valuable because it shows intent, but it is not the same as a Terraform plan. Changing a module source version can produce a large infrastructure difference with a small text diff. A plan connects the source and inputs to the current state and provider observations.

Repository permissions are part of deployment security. If someone can modify a workflow that receives production credentials, they may be able to change how those credentials are used. Protect the source and workflow paths that define privileged execution, and make review requirements match that authority.

10.3 Separate untrusted checks from credentialed operations

A pull request from an untrusted contributor can run harmless syntax and unit checks in a restricted context. It should not automatically receive a privileged cloud role. Terraform configurations can include executable integrations, so merely limiting the intended command to plan does not make arbitrary source safe to execute with credentials.

Even read-oriented plan roles can expose sensitive state and infrastructure metadata. A plan job's privilege is not zero. Decide which source revisions and event types may receive that role, and keep untrusted contribution workflows separate from protected deployment workflows.

Avoid a workflow pattern that checks out untrusted code in a privileged event context and then runs it with secrets or OIDC authority. The security boundary depends on the event, checkout target, repository permissions, runner, action code, and cloud trust policy together.

The course does not activate any hosted workflow or create a repository. Its portable pipeline is complete code that you can run locally and adapt to your existing CI system. The included CI adapter notes state the runner and trust prerequisites rather than pretending that a YAML file alone configures repository protection.

10.4 Use short-lived cloud identity through a constrained trust

OpenID Connect, or OIDC, allows a CI platform to present a signed identity token that a cloud role trust policy can validate. The role session then uses temporary AWS credentials. This avoids storing a permanent access key as a repository secret, but it does not eliminate authorization design.

For GitHub Actions with AWS, the trust needs an intended audience and a constrained subject representing the authorized repository/ref or environment pattern. An unconstrained trust can allow unintended workflows to request the role. AWS permissions on the role should then limit what the resulting session can do.

GitHub's OIDC for AWS guide and the official AWS credential action explain the integration. This is an architecture example; no identity provider or role is created by reading the chapter or running the local-only checks.

Separate planning and applying roles where that improves the trust model. The plan role needs backend read/locking behavior and relevant read APIs; exact requirements depend on the provider operations. The apply role needs approved mutation authority. Both roles may need additional constraints such as permission boundaries and account allowlists.

Do not claim a universal minimal policy for every Terraform plan. Data sources, refresh behavior, and resources vary. Derive policies from the supported workflow and validate them, including explicit denies and organization controls.

10.5 Define a stable run identity

A deployment run should identify its root, backend/state scope, account/region, source revision or source fingerprint, CLI version, provider lock selection, input identity, artifact digests, and plan digest. These are related but independent dimensions.

The supplied pipeline computes a source fingerprint over the course's relevant Terraform and artifact source files and records the saved plan's SHA-256 digest. It also records the selected CLI version and root path relative to the course. The manifest is a consistency record, not a cryptographic signature or an independent authorization service.

If an attacker can replace both the plan and manifest in an unprotected directory, hashes alone do not prove provenance. Production CI should protect artifacts, job identity, access, and approval records. A signed attestation can add stronger provenance under a suitable key and trust system; it still needs a verified relationship to the executor.

The source fingerprint intentionally includes shared module files, not only the root's main.tf. Otherwise a changed child module could slip between planning and applying without changing the root file. Application artifact bytes are included because the function package is part of the deployment input.

10.6 Handle Terraform's detailed exit codes correctly

terraform plan -detailed-exitcode uses zero for a successful no-change plan, two for a successful plan containing changes, and one for an error. A generic shell failure rule that treats two as an error can break a correct plan job. A permissive rule that ignores every nonzero result can proceed after a real failure.

The pipeline handles these outcomes explicitly. It accepts zero and two, rejects one or unexpected failures, and only then renders plan JSON and runs policy. This is an example of adapting automation to a tool's actual contract rather than guessing from common conventions.

A no-change plan can still contain output updates or other representation details that deserve appropriate handling. Read the actual plan and manifest. The code does not use a hard-coded expected resource count as a substitute for review.

The CLI wrapper option in hosted setup actions can also affect how output and exit codes are exposed. If using HashiCorp's setup action, understand its documented behavior and select wrapper settings deliberately. The portable Python pipeline invokes the native Terraform executable directly.

10.7 Run a complete local planning pipeline

With Terraform and Python available on PATH, use the local lab first:

python ./scripts/pipeline.py plan --root labs/00-local --out .runs/local-review

The command checks the root is inside the course labs, initializes it with the declared dependency behavior, validates it, creates a saved plan, writes its JSON representation, evaluates the narrow policy, and writes a review manifest. It does not apply the plan.

Read the printed paths. Inspect the human-readable plan through Terraform and inspect the manifest. The output directory can contain sensitive plan data when used for AWS roots, so use a protected directory and a short retention policy. The local exercise contains only synthetic data.

The .runs directory is ignored by the course's source-control rules. Ignoring a directory prevents accidental normal Git addition; it is not an access-control mechanism. On a shared runner, configure filesystem permissions, artifact permissions, and cleanup through the runner platform.

For an AWS root, establish the backend and approved identity first, provide the root's actual nonsecret inputs, and use the same command with the intended lab root. The provider account allowlist remains an additional check. The pipeline deliberately does not create a missing cloud identity or silently choose a different profile.

10.8 Authorize one concrete saved plan

After reviewing the plan, the pipeline's apply command requires its manifest and the plan digest as an explicit approval argument:

python ./scripts/pipeline.py apply --manifest .runs/local-review/manifest.json --approve PLAN_SHA256_FROM_REVIEW

Replace the displayed placeholder with the actual digest from the manifest after review. The script verifies the plan bytes, relevant source fingerprint, CLI version, root, and age before invoking Terraform with the saved plan. A stale state can still make Terraform reject application; the script does not bypass that native protection.

The digest is not a password. Requiring it makes the selected proposal explicit in this educational workflow. In production, a protected approval gate should bind an authorized reviewer and approved artifact/run identity. A caller who can run the apply command already has meaningful local authority.

Do not rebuild the Lambda ZIP after planning and before this apply. If the source or artifact changes, generate and review a new plan. Do not edit the manifest to make a mismatch disappear. The mismatch is evidence that the proposed execution context no longer matches the reviewed one.

10.9 Plan age is a policy choice

The pipeline uses a four-hour default maximum age. This is a teaching policy, not a universal Terraform requirement or a guarantee that any younger plan is safe. A rapidly changing production system may need a much shorter review interval. A carefully frozen maintenance window may support another bound.

Relevant state changes can invalidate a plan regardless of wall-clock age. External service behavior and permissions can also change without updating the state serial. A recent plan reduces some uncertainty but does not eliminate the need for post-deployment verification.

When a plan expires, regenerate it and obtain the appropriate review. Do not treat approval as permission to keep recalculating different plans until one happens to apply. If the new plan is materially different, explain the difference and review it as a new proposal.

A deployment system should make this workflow convenient enough that people do not work around it. Clear artifacts, concise summaries, and fast local checks support safety by reducing unnecessary friction.

10.10 Protect and serialize the apply boundary

Use one concurrency key per state identity for applies. If the key is only the repository name, unrelated roots may block each other unnecessarily. If the key is only the branch name, two branches may modify the same state concurrently. The correct unit follows the actual backend/state ownership.

Backend locking remains enabled. Pipeline serialization coordinates jobs known to the CI system; backend locking coordinates clients using the same backend. Neither prevents another state from managing the same object, so ownership discipline remains essential.

A protected environment can impose approvals or branch restrictions depending on the CI platform and account plan. GitHub documents environment behavior and availability in deployment environments. Merely writing an environment name in YAML does not prove that required reviewer rules exist or are available for the repository's plan.

Verify protection through the actual repository settings and a controlled test. Record who can change those settings. An approval gate that a deployment author can silently disable may not provide the separation of duties the organization assumes.

10.11 Apply is followed by observation, not celebration

After Terraform succeeds, run probes tied to the change's purpose. For the health API, retrieve the endpoint, call it, and verify the expected release. For a network change, verify the relevant source-to-destination path. For a backend migration, verify associations and a normal plan. For a data-store change, verify the required data behavior and recovery properties.

Record the apply outcome and probe results with the same run identity. A failed probe should initiate diagnosis rather than automatically declaring infrastructure rollback safe. The appropriate response depends on what changed and which recovery path was designed.

Logs can contain sensitive data, so capture narrow evidence. A health response with status and release is enough for this demonstration; there is no reason to archive every environment variable or full state snapshot in a public build summary.

A periodic drift plan can detect later differences, but recurring scheduling is an operational choice for your team. This course describes how to interpret those results and does not create any standing cloud job or automation in your account.

10.12 Cache dependencies without caching authority

Provider caches can reduce download time. They should preserve integrity checks and be scoped to avoid untrusted jobs poisoning privileged execution. A cache is an optimization, not the authority for which package is allowed; lock records and trusted distribution still matter.

Do not cache credentials, initialized backend metadata containing sensitive configuration, state files, or plan artifacts as if they were harmless package data. A broad “cache the entire working directory” rule can retain exactly the operational information you intended to keep short-lived.

Application build caches have similar considerations. A reproducible artifact should be identified by its bytes and produced in a trusted context. If a privileged deployment accepts arbitrary cached output from an untrusted pull request, the source review may no longer describe the deployed code.

The course archive excludes .terraform, plugin caches, run outputs, and authoring dependencies. It includes dependency lock records and readable source. That packaging choice models the distinction between reproducible inputs and machine-local execution data.

10.13 Failure paths need explicit behavior

If formatting fails, stop before cloud access. If initialization cannot verify dependencies, stop rather than falling back to an unknown provider. If validation fails, report the relevant diagnostic. If policy fails, preserve the protected plan for review and do not invoke apply.

If apply fails partway, preserve the state and diagnostics, stop other writers, and calculate a fresh plan after addressing the cause. Do not rerun an old saved plan after manually changing infrastructure and assume it still represents the system. If the runner disappears, inspect lock ownership before any force-unlock action.

If the application probe fails, compare the expected release, artifact hash, handler behavior, role, invocation permission, and logs. The evidence chain narrows the problem: you know which package and infrastructure proposal were intended, so you can investigate the actual mismatch.

If a secret leaks into logs or artifacts, treat it as a credential/data incident under the appropriate process. Removing the visible line from the current file does not erase historical artifacts. Rotation, access review, and retention cleanup may be required depending on the secret and exposure.

10.14 AI assistance fits inside the review boundary

An AI assistant can explain a plan, propose a module refactor, or draft tests. It should not be treated as an authority that makes a risky plan safe merely by describing it confidently. Give it the smallest nonsecret context required and verify the proposed code against primary documentation and executable checks.

A useful review prompt is: “Review this sanitized Terraform diff and plan summary for address changes, replacements, widened permissions, state-boundary mistakes, and missing recovery steps. State uncertainty, cite the relevant official schema, and do not propose application until the concrete plan is reviewed.” This is a prompt you may choose to use; it is not an action performed by the course.

For code generation, ask for a complete change with explicit inputs, provider baseline, supported paths, tests of meaningful behavior, and a statement of what was not executed. Avoid pasting raw state or secret-containing plan JSON into an external assistant without an approved data-handling basis.

The best use of assistance is to make reasoning and evidence clearer. Retain human accountability for authorization, organizational context, and the operational consequences of the change.

10.15 Optional application and reference direction

Run the planning pipeline for the local lab. Copy the manifest's plan digest into the apply command after review and verify that the local resources appear. Then change a relevant source file in a scratch copy and try to apply the old manifest. The expected reference behavior is rejection before Terraform application because the source fingerprint changed.

Restore the source or create a new plan; do not edit the recorded fingerprint. Separately, change a byte in a copied saved plan and confirm its digest check fails. These experiments demonstrate consistency checks, not protection against an attacker who controls both the trusted runner and all artifacts.

For a CI design exercise, map the portable stages onto your organization's runner. Identify the untrusted event boundary, cloud role trust conditions, protected artifact store, state concurrency key, approval mechanism, and post-apply probe. A reference design names the actual authority at each point rather than writing a single job with permanent administrator keys.

Worked runner contract: map the portable pipeline onto CI

A CI adapter needs less hidden machinery when the underlying workflow is already an executable script. Define a runner image containing the selected Terraform CLI, Python, and any required build tools. Record the image identity and update process. Then map events and stages onto the portable commands rather than reproducing their logic inconsistently in several shell snippets.

An untrusted validation stage can run formatting, Python tests, local Terraform tests, and mocked module tests without cloud credentials. It still needs network/dependency controls and bounded runner resources. It should not read production state, receive the deployment role, or upload arbitrary local files as public artifacts.

A protected plan stage checks out an approved source revision, obtains the planning identity, initializes the intended backend, supplies explicit environment inputs, builds or retrieves the approved application package, and runs pipeline.py plan. It retains the saved plan, JSON, and manifest in a protected short-lived store. The human-readable summary should identify meaningful actions without dumping secret values.

An approval stage binds an authorized reviewer to that run and plan digest. Its mechanism comes from the actual CI platform and repository settings. A string variable called APPROVED=true in source is not an independent reviewer. Verify that the person proposing the change cannot silently redefine the approval control when separation is required.

A protected apply stage retrieves the same source and artifacts, obtains the applying identity, verifies context, serializes against the state, and invokes the saved-plan command. It does not run a fresh unconstrained apply as a substitute. Afterward, a probe checks the expected release and relevant service properties.

What the portable script verifies

The script constrains roots to this course's labs, checks formatting and configuration, saves a detailed plan, evaluates the included narrow policy, and records a SHA-256 digest. At apply it compares the plan bytes, relevant source/artifact fingerprint, CLI version, root location, and age. Terraform itself then enforces its saved-plan/state consistency behavior.

The fingerprint includes ordinary Terraform source, test configuration, lock records, local variable files, Python tooling, and the packaged ZIP in the selected source areas. It deliberately excludes generated state and provider caches. The aim is consistency of reviewed deployment inputs, not a general repository integrity monitor.

The script does not authenticate the human reviewer, inspect repository branch protection, verify a cloud OIDC trust, or prove that a manifest came from a trusted job. It also does not record secret environment values in the manifest. Saved plans retain planned ordinary input values, while credentials and supported ephemeral values have different runtime handling. Production integration must verify the execution identity and protected artifact provenance separately.

This explicit limit is important. Hashes answer whether bytes match an expected digest. A signature or trusted platform record can help answer who vouched for that digest. Authorization decides whether that actor may approve deployment. These are related but distinct claims.

A complete stage handoff record

A useful handoff record can contain a run ID, source commit/fingerprint, root/state identity, target account/region, CLI version, provider lock digest, package digest, plan digest, policy result, creation time, reviewer identity, and expiry. Avoid copying secret values into the record to make it appear more complete.

At apply, compare the actual context to the record. If the cloud role is wrong, stop even if the file hashes match. If the root/state key is wrong, stop even if the source commit is right. If the plan bytes differ, stop even if the filename is unchanged. Each check protects a different link.

After application, append the executor/run result and probe evidence through the CI platform's normal record system. The manifest shipped by the educational script remains a consistency artifact, so do not retroactively edit it to describe a different plan or package.

Work through a rejected apply

Assume a plan was reviewed at 10:00 for package A. At 10:15 a developer rebuilds the ZIP from changed source into the same filename. At 10:20 the apply stage compares source/artifact fingerprints and refuses. The correct response is a new build identity and a new reviewed plan, not manually copying the old digest into the new manifest.

Now assume the package is unchanged but another valid deployment updates the state at 10:18. Terraform may reject the old saved plan as stale. Again, replan against the new state and review the result. The previously approved intent may still be desirable, but the executable proposal must be recalculated in the current context.

Finally, assume the plan and state are unchanged but the apply role loses permission. Execution can fail despite a valid plan. Preserve partial results and diagnose the authorization boundary. A plan is not a reservation of future permissions or service capacity.

Keep summaries useful and nonsecret

A CI summary should lead with destination, root, source/run identity, and meaningful changes. List replacements and deletions explicitly. Summarize the purpose of IAM changes rather than printing every sensitive value. Link authorized reviewers to the protected full plan when deeper inspection is necessary.

If a generated plan is too large to review coherently, investigate broad dependencies, accidental churn, provider upgrades mixed with feature changes, or an overly broad root. Truncating the plan until it looks small does not reduce the operational change. Improve the change's structure and explanation.

A failed job should identify the failed stage and next useful action. “Pipeline failed” alone forces the next operator to reconstruct the entire workflow. A precise message such as “plan digest differs from reviewed artifact; generate a fresh review” points directly to the consistency boundary.

Preserve a usable emergency path

A protected delivery process still needs an incident procedure for unavailable runners, expired identity integrations, or urgent restoration. Define who may authorize an exceptional run, which identity is used, how state locking remains intact, and how the action is recorded afterward. An emergency path should preserve accountability rather than becoming a permanent shortcut around normal review.

If a manual apply is authorized, use the intended source, dependency lock, inputs, backend, and account checks. Capture the concrete plan and outcome under appropriate access controls. After service recovery, reconcile the normal pipeline with the actual state so the next automated run does not undo the emergency change unexpectedly.

Do not store a permanent administrator key in a shared document as the emergency design. Use the organization's approved identity recovery mechanism and test that authorized operators can obtain it when the normal CI system is unavailable.

The educational pipeline intentionally remains smaller than a full enterprise control plane. Its value is that you can inspect every consistency check and map it onto a real authority model. Keep that distinction visible when adapting it: add the platform controls your organization actually needs, verify their settings, and avoid claiming that an extra script argument creates independent approval.

11. Multi-account architecture, data services, and platform operations

Central problem: How do we preserve understandable ownership and safe change when infrastructure spans accounts, regions, data lifecycles, and many teams?

Prerequisites: all earlier chapters, especially independent provider/backend identities, module contracts, migration, and delivery evidence. Source examples include the target-account root and the optional RDS root.

11.1 Scale the ownership model before scaling the code

An organization can have thousands of Terraform resources while retaining clear authority, or a few dozen resources with confused ownership. Resource count is not the first scaling question. Start with who owns each root, which account and state it operates on, what other systems depend on its outputs, and how it is recovered.

An account is a useful isolation boundary for permissions, quotas, billing relationships, and incident scope. An organizational unit groups accounts under common governance. Service control policies and related organization controls can limit permitted actions, but they do not grant workload permissions merely by existing. A deployment role still needs applicable authorization.

A platform design often separates organization/bootstrap, security/logging, shared networking, and workload accounts. These are architectural patterns rather than a requirement to create an account for every diagram box. The correct boundaries depend on regulatory needs, team ownership, scale, costs, and operational maturity.

Do not give a learning Terraform root authority over the management account to make cross-account examples convenient. The course's multi-account root assumes a deployment role that already exists under an authorized account setup. Its source is complete for that contract, but the trust relationship and organizational governance are prerequisites supplied by the organization.

11.2 Trace a cross-account role session

The target-account root begins with a source profile, a target account ID, a deployment role name, and a region. The provider uses the source profile, assumes the target role, and checks that the resulting account is the intended target.

provider "aws" {
  alias               = "target"
  region              = var.region
  profile             = var.source_profile
  allowed_account_ids = [var.target_account_id]

  assume_role {
    role_arn     = "arn:aws:iam::${var.target_account_id}:role/${var.deployment_role_name}"
    session_name = "tf-mastery"
  }
}

This fragment comes from the complete root and assumes the ordinary provider requirements. The source identity must be allowed to request the role session, and the target role's trust must permit the request. The resulting role permissions, session constraints, boundaries, and organization controls then limit actions.

The alias target is mapped into the private-bucket module through its providers argument. The child receives an AWS configuration appropriate to the intended account without hard-coding the account itself. This is the module/provider separation from Chapter 7 applied to a real organizational boundary.

The backend is still independent. In this example it remains local unless you configure one. A production tooling-account backend would need its own explicit identity and access design. Provider role assumption does not transport state into the target account or make the backend role equivalent.

11.3 Organization guardrails are limits, not ordinary grants

A permission boundary or service control policy can restrict what an identity is allowed to do, even if an attached policy appears broad. An explicit deny can override an allow. Resource policies introduce additional evaluation paths and nuances, especially across accounts and for different principal forms.

AWS's policy evaluation logic is the primary reference. Do not reduce the entire system to “all policies are intersected” or “any allow wins.” The result depends on policy type, principal, resource context, and explicit denies.

A deployment role may be permitted to create application roles only when a required permissions boundary is attached. Terraform needs to model that boundary on created roles, and the executor may need appropriate PassRole permissions scoped to the intended services and roles. A broad IAM wildcard added to fix one failure can undermine the governance design.

When a plan fails in one account but succeeds in another, compare organizational controls and role/session context as well as Terraform code. Identical configuration is not identical authority. Record the account's guardrails as part of the environment contract so developers can understand legitimate failures without guessing.

11.4 Multi-region means duplicated dependencies and explicit failover

A provider alias can select another region, but a multi-region application also needs data placement, artifact availability, DNS/routing, certificates, service support, capacity, and failover behavior. Duplicating a function resource is only one part of the design.

Some resources have regional identifiers and cannot be reused unchanged elsewhere. AMIs, subnets, and many service endpoints are regional. Certificate placement can have service-specific requirements. An architecture that passes Terraform validation can still reference a resource in the wrong region for the consuming service.

Decide whether the secondary region is active, warm standby, or a recovery target. Those choices affect cost and recovery time. Define how traffic shifts, how data consistency is maintained, and how the team determines that the secondary is ready. Test failback as well as failover where the business requires it.

Terraform should encode the infrastructure and chosen relationships, while the runbook describes operational decisions and evidence. A single apply across two regions is not a transaction and can partially succeed. Separate state boundaries can improve isolation while increasing orchestration needs; choose based on failure and ownership requirements.

11.5 Data has a different lifecycle from compute

A health function can be replaced from a known package. Customer data cannot generally be reconstructed from Terraform source. Persistent storage therefore needs backup, retention, deletion, migration, and recovery decisions that remain meaningful even when the infrastructure definition changes.

For DynamoDB, the capstone uses on-demand billing, server-side encryption, and point-in-time recovery. The table's partition key is release_id. These settings configure a storage service; they do not seed records or implement the application logic. On-demand mode removes a particular provisioning decision but does not make usage free or eliminate account/service limits.

A partition key determines how access patterns map onto the service. A poorly chosen hot key can concentrate load. Terraform can enforce the declared key schema but cannot infer the application's query patterns. Design the data model from required reads and writes, then choose indexes and capacity/usage controls accordingly.

Point-in-time recovery supplies recovery options under service semantics. It does not mean a user can undo any operation instantly within the same table. Restoring and switching an application to a recovered target is an operating procedure with permissions, validation, and possibly downtime considerations.

11.6 RDS introduces maintenance, secrets, and deletion protection

A relational database stores structured data under an engine such as PostgreSQL. RDS manages parts of provisioning and operations, but the user still chooses networking, engine versions, instance capacity, backups, maintenance behavior, credentials, and application compatibility.

The optional labs/09-rds root creates a private subnet group using the network module, a client security group, a database security group allowing PostgreSQL only from that client group, and an RDS PostgreSQL instance. It does not create a client instance or application, so actual connection testing requires an authorized client placed in the intended network and given appropriate credentials.

The root requires an explicit engine version, instance class, and unique final-snapshot identifier. Those values are region- and time-sensitive; use the AWS service's current supported offerings rather than copying an obsolete hard-coded example. The teaching root defaults to a single-AZ database to keep the architecture visible, while making the production availability decision explicit.

The database enables encryption, managed master-password handling, backup retention, and deletion protection. It is not publicly accessible. apply_immediately is false, so some changes may wait for maintenance behavior rather than taking effect at the moment the Terraform operation returns. The pinned RDS resource schema describes supported settings and update implications.

This lab is optional and can incur material recurring cost. It is not part of the default serverless capstone. Deletion protection must be deliberately changed and reviewed before a planned teardown, and the final snapshot has its own retention and cost consequences.

11.7 Work a database capacity change through its real lifecycle

Suppose a database is approaching storage pressure. The configuration currently requests an allocated size and permits autoscaling up to a maximum. First inspect actual usage, growth rate, engine limits, and the service's current modification state. Do not infer urgency from a Terraform diff alone.

If the desired change increases storage, inspect whether the service supports the transition, whether it can be reversed, and when it becomes effective. Some storage changes cannot be undone by reducing a number in code. A Git revert does not guarantee an in-place shrink.

Plan with the correct provider and state. Read maintenance-related arguments, immediate-apply behavior, and any pending modifications. A subsequent plan may continue to show a difference while AWS is waiting for a maintenance window. Repeatedly applying or forcing replacement can turn an expected pending transition into an incident.

Define application checks and a recovery strategy before the change. A backup should be recent enough and restorable under the required recovery objective. Verify how the application finds the database endpoint and obtains credentials. If recovery creates a new database instance, connectivity and secrets may need a controlled cutover.

After the service reports the intended state, inspect metrics and application behavior. Record the observed capacity and any follow-up actions. The useful evidence is the whole transition from measured need to service state and application health, not merely a successful Terraform exit code.

11.8 Provider upgrades are schema and behavior changes

A provider implements resource schemas, diff logic, API calls, retries, import behavior, and state migrations. Upgrading it can change plans even with identical configuration. A release note that sounds small can affect a critical resource's computed attributes or replacement behavior.

The course intentionally fixes AWS provider 6.0.0 for reproducibility. To adopt a newer version, choose a reviewed target, read official upgrade and release notes, update constraints in the relevant roots/modules, initialize with the intended upgrade behavior, and inspect lock-file changes. Do not let a routine validation job silently select the target for you.

Test representative fresh deployments and existing-state upgrades. Fresh-state tests reveal schema compatibility; existing-state tests reveal migration and diff behavior. Include critical resource categories such as IAM, network, storage, and data services in the representative set.

Plan in a lower-risk environment first, then roll out across roots in stages. Keep the old configuration and evidence, but do not assume provider downgrade is a safe rollback after a newer provider has written state. State schema compatibility can constrain reversal.

A module supporting a range of provider versions should maintain a meaningful test matrix. A lower-bound constraint without tests is only a claim. Narrow support may be appropriate for an internal module if the organization prefers coordinated upgrades and can support that operational model.

11.9 Diagnose provider behavior using the right interfaces

terraform providers shows provider requirements and relationships. terraform providers schema -json exposes the selected provider's schema in structured form. These can help distinguish an unsupported argument from a documentation mismatch.

A resource diagnostic may originate in Terraform's language evaluator, provider validation, or the remote AWS API. Read the message and context carefully. An “unsupported argument” before any API request usually calls for schema/version inspection, while an AWS request ID suggests the service received a request.

Detailed Terraform logs can help investigate difficult issues, but they may expose sensitive values. Enable them narrowly, store them securely, and remove them according to the incident process. Do not ask a colleague to post an entire debug log publicly without reviewing its contents.

When reporting a provider defect, build a minimal nonsecret reproduction with the exact CLI/provider versions, resource configuration, expected behavior, actual behavior, and relevant diagnostics. Reduce unrelated modules so maintainers can see the underlying interaction. A careful reproduction is often more useful than a long description of the original repository.

11.10 Optimize plans by reducing unnecessary work

Large roots can suffer from slow refresh, broad dependency edges, expensive data lookups, provider API rate limits, and excessive computed churn. Begin by measuring where time is spent. Splitting files does not split state or reduce the graph's operational scope.

Use direct references and stable published interfaces rather than repeated account-wide discovery queries. Avoid broad module dependencies that make unrelated data sources defer until apply. Keep resource ownership coherent so two declarations do not continually overwrite the same property.

The -parallelism setting can limit concurrent operations. Increasing it may improve throughput until API limits or service dependencies dominate; decreasing it can reduce pressure in particular incidents. It is not a substitute for correct dependencies, and a faster failing run is not an improvement.

Split roots when ownership, lifecycle, risk, or independent deployment justify it. Every split adds cross-root orchestration and interface obligations. A monolith can be too broad; an extreme collection of tiny states can be too brittle. Measure coordination cost alongside plan duration.

11.11 Hosted execution changes the operating surface

HCP Terraform and Terraform Enterprise can supply managed state, execution, permissions, policy integration, and other platform capabilities. Exact feature availability depends on the product and plan and should be checked in current official documentation before adoption.

Remote execution moves the credential and network boundary. A run may execute in a hosted environment or an agent connected to private infrastructure. A successful local plan does not prove the remote runner has the same files, variables, provider access, network paths, or identity.

A remote-execution design should identify who can queue plans, approve applies, change variables, read state, manage agents, and alter policy. These are distinct authorities even when a platform makes them easy to configure. Preserve the evidence chain from Chapter 10 in the chosen execution model.

The course does not provision or claim to test a hosted account. The local pipeline teaches the invariants that remain useful when the execution platform changes. Evaluate a platform based on the real control and operational needs it solves, not the assumption that “remote” inherently means correct.

11.12 Stacks coordinate a different configuration layer

Terraform Stacks are an HCP Terraform configuration layer for composing components and deployments. They differ from ordinary root modules and workspaces and require their own current documentation and execution context. They can be relevant when coordinating repeated module-based infrastructure across environments at scale.

The Stacks overview was inspected for this edition's architectural survey. The course does not provide a fake locally executable Stack or claim that ordinary CLI roots automatically gain Stack orchestration by renaming files.

Before adoption, map existing ownership, state, outputs, provider configurations, rollout requirements, and failure recovery to the platform's actual model. A new orchestration layer can simplify repeated deployment while introducing migration and operating responsibilities of its own.

The expert skill is to recognize when ordinary roots and a clear pipeline remain sufficient and when a coordinated platform offers concrete value. New syntax is not a learning objective by itself; a better-supported operational model is.

11.13 Actions and discovery need provider support

Current Terraform documentation includes provider-defined actions for operations outside ordinary managed-resource state transitions. Availability depends on the provider implementing the action and on the selected CLI/platform context. The course's older pinned AWS provider baseline is not claimed to support every new action described in current documentation.

The action invocation guide distinguishes these operations from managed resource state. Before using an action, identify its side effects, retry behavior, authorization, audit trail, and relationship to resource lifecycle. A convenient trigger can still perform a consequential external operation.

Discovery and query workflows can assist adoption of existing infrastructure, but documentation and provider support are evolving. Some specific list/query reference pages were unavailable through the research interface for this edition; the source ledger records that limit. The book therefore does not invent runnable list-block APIs or imply they were tested.

The stable adoption principles remain: identify the actual object, establish one owner, produce reviewable configuration, plan the association and changes, and verify the resulting state. A discovery tool can accelerate inventory without deciding those responsibilities for you.

11.14 Kubernetes and application controllers create ownership edges

If Terraform creates an EKS cluster and immediately configures a Kubernetes provider using values from that new cluster, initialization and readiness dependencies can become difficult. A separate cluster-foundation root and workload deployment process often make the boundary clearer.

Kubernetes controllers continuously reconcile workloads. Terraform also reconciles declared infrastructure when invoked. If both own the same field, they can fight. Choose an owner for replica counts, generated annotations, certificates, and other dynamically managed attributes, then encode that delegation deliberately.

The same principle applies outside Kubernetes: an autoscaler, secret rotation service, configuration agent, or incident script can be a legitimate external writer. Document ownership at the attribute level where necessary. Do not globally ignore changes just because a controller exists somewhere in the architecture.

A platform team should publish supported interfaces rather than requiring application teams to read cluster state containing unrelated authority or secrets. Versioned outputs, runtime identity, and independent workload delivery can preserve useful separation while still allowing coordinated upgrades.

11.15 Work an organizational rollout as a staged change

Suppose the platform team wants all artifact buckets to require TLS and preserve version history. First inventory module consumers and identify unmanaged exceptions. Define the new contract and migration behavior. Test a representative existing bucket so the team knows whether the change is in place, whether policy conflicts exist, and whether any application uses an unsupported access path.

Release the module with clear notes and an adoption window. Upgrade a development root, inspect its plan, apply, and verify relevant access behavior. Then promote through representative staging and production roots with their own state and approvals. Track actual adoption rather than assuming publication means enforcement.

If a consumer has a legitimate exception, document it explicitly with an owner and rationale. Do not silently add a generic bypass flag that every future consumer can select without review. A controlled exception preserves the meaning of the standard contract.

Observe the rollout's failures. AccessDenied can indicate an unexpected client behavior, a policy conflict, or a flawed implementation. Use evidence to refine the change. Organizational scale is often a coordination and communication problem as much as a Terraform syntax problem.

11.16 Architecture decisions should record tradeoffs

A short architecture decision record names the problem, constraints, considered alternatives, selected choice, consequences, and revisit trigger. For example, “Use separate workload accounts because production authority and recovery must be isolated; accept additional role/bootstrap coordination; revisit shared tooling when the number of accounts exceeds the team's manual operating capacity.”

Useful revisit triggers are concrete: a measured request rate, a recovery-time objective, a compliance requirement, a number of independent teams, or a cost threshold. “Revisit when scale grows” is too vague to guide action.

The companion's Architecture tradeoffs experiment computes an explanatory recommendation from chosen workload and operating constraints. It is a transparent educational decision model, not an automated architect. Inspect its assumptions and use it as a starting point for a written decision, then validate service-specific feasibility through current primary sources.

Worked state-boundary decision: one platform, three teams

Suppose a networking team owns VPCs, a data team owns RDS, and an application team owns the health/API tier. All three currently share one state and one deployment role. An application wording change can require access to database settings and networking plans, while a network change risks locking every other team out of deployment.

A proposed split gives each team a root with its own state, role, and approval path. The network publishes a stable subnet/security interface. The database root consumes that interface and publishes a nonsecret endpoint/secret reference through an approved channel. The application root consumes only what it needs. This improves authority separation but introduces compatibility and ordering obligations.

A routine compatible application release should not require a network apply. An incompatible subnet migration does require coordinated consumer changes. The platform needs a documented interface version and migration path rather than assuming that separate states can never affect each other.

Compare failure modes explicitly. In the shared root, one lock or plan error can block all teams, but a single plan sees more of the graph. In split roots, teams can move independently, but no single plan proves cross-root compatibility. The decision should follow team authority and lifecycle, then be supported with orchestration and contracts.

Audit an assumed role's real authority

For a role that deploys Lambda, identify why it needs each category: function lifecycle, role creation/policy management where permitted, PassRole to the intended function role, API configuration, logging configuration, state access, and selected read operations. Scope resources and conditions where AWS supports them. A role that can create arbitrary roles and pass them to arbitrary compute may have much broader effective authority than a simple action list suggests.

If the organization requires a permissions boundary on created roles, encode it in the module contract and test its presence. Verify that the executor cannot simply remove the boundary. IAM design includes both the role being created and the authority of the actor creating it.

The course source omits organization-specific boundary ARNs because inventing one would make the example falsely concrete. A production adaptation should add an explicit validated input or platform-owned provider/module context and document the required governance behavior.

Upgrade a fleet of roots in cohorts

Group roots by representative risk rather than upgrading every state at once. A first cohort might include a disposable environment and a service with good probes. A later cohort includes persistent data and critical networking. Define stop criteria such as unexpected replacement, repeated drift, provider crashes, or probe failures.

Preserve the exact provider version and lock record for each cohort. If an issue appears, pause rollout while unaffected roots remain on their prior baseline. Do not assume that downgrading already-upgraded state is safe; investigate schema compatibility and a forward correction.

A rollout record should identify actual applied roots, not merely repositories with merged version bumps. A merged dependency change can remain unapplied for weeks. Platform inventory and execution evidence close that gap and support later incident diagnosis.

Decommission an interface as carefully as you introduce it

A platform output, role, or shared service can outlive its original owner. Before removal, identify actual consumers, announce a supported replacement, measure adoption where possible, and define the final retirement condition. A search of one repository may miss consumers in another account or operational tool.

For a deprecated module output, retain compatibility through the promised upgrade window. For a role, verify which workflows still assume it before deleting trust. For a backend bucket, identify every state and recovery dependency before retirement. These are versions of the same ownership problem at different scales.

A practical inventory should connect resource, owner, state, consumers, data sensitivity, and recovery obligations. It does not need to begin as a complicated product; an accurate maintained register is better than an ambitious abandoned dashboard.

Expert operation includes reducing unnecessary infrastructure and interfaces. Removing a component with evidence can improve security, cost, and understandability. Treat decommissioning as an engineered migration with explicit retention and verification, rather than a cleanup spree driven by names that look old.

When account boundaries change, verify physical zone alignment through zone IDs where cross-account placement requires it. Matching zone-name letters are not sufficient evidence. Keep this placement decision separate from provider aliases and state paths, which describe different relationships.

A reference answer includes the verified target account, permitted role session, intended bucket/state ownership, and a reviewed plan under that identity.

For the RDS extension, choose current supported values in a sandbox only if you intend to incur and manage the cost. Review deletion protection and final-snapshot behavior before creation, not during an impatient teardown. No actual database deployment was performed during course authoring.

12.10 Rehearse drift as an operating decision

Use a disposable setting in your sandbox, such as a harmless tag, to observe a deliberate out-of-band change. Run a normal plan and inspect how Terraform proposes to reconcile it. Decide whether to adopt the changed intent in configuration or restore the declared value.

Do not use a public-access flag or production permission as a casual drift experiment. The learning objective is observing reconciliation, not creating avoidable exposure. A synthetic tag provides the same mechanism with lower impact.

If an external controller legitimately owns a value, document that ownership and choose a precise delegation. Do not add ignore_changes to the entire resource to suppress an inconvenient plan. The reference capstone has no external autoscaler or controller claiming its declared settings.

A drift runbook should say how alerts are triaged, who decides whether a change is legitimate, and when a new reviewed apply is appropriate. Automatic reconciliation may be suitable for some environments, but it must account for incidents and authorized emergency changes rather than treating every console action as malicious or every difference as harmless.

12.11 Practice recovery without manufacturing a data incident

The supplied local migration lab demonstrates identity-preserving change. Use it for deliberate state/address exercises. For the real capstone, practice locating backend versions, identifying the correct key, and explaining the restore procedure without randomly replacing state snapshots in a live deployment.

For storage recovery, use a tiny synthetic object in the artifact bucket and observe versioning behavior. Restore or retrieve a prior version through the service's supported workflow. Record the object key and version identifiers in a protected note. This demonstrates an actual storage recovery mechanism without involving company data.

For DynamoDB, understand that point-in-time recovery operates under service-specific restore semantics and may create another table. A complete data recovery rehearsal needs write traffic assumptions, validation, application configuration changes, and cutover decisions. The capstone does not claim to execute that rehearsal automatically.

The expert lesson is that a recovery capability must be tested at the layer it promises to recover. Terraform state versions help management recovery. Object versions help object recovery. Database backups help database recovery. None is a universal substitute for the others.

12.16 Learn from incidents without normalizing improvisation

Expertise includes recognizing uncertainty early, choosing the next discriminating observation, and preserving recovery options. During an incident, a small deliberate change can be better than a broad refactor. Afterward, capture the mechanism, evidence, and corrective action while the details are still available.

A useful incident analysis separates the triggering change, contributing conditions, detection, impact, recovery, and prevention. “Human error” is rarely a sufficient technical explanation. A wrong-account apply may reveal missing destination checks, weak role separation, unclear root naming, or an approval that did not bind the actual plan.

Turn repeatable lessons into the appropriate control: a type validation, module contract test, plan rule, narrower role, clearer output, documented migration, or better probe. Do not add every conceivable control to every workflow. Choose the one that addresses the observed failure mechanism with acceptable operating cost.

Keep the educational examples small enough to understand, then practice the same reasoning on supervised real changes. Reading can supply concepts and patterns; expert judgment grows through feedback from actual systems and accountable operation.

The operator notes that neither the health probe nor the local migration proves DynamoDB restore behavior, multi-region availability, or authenticated application CRUD.

This is a strong record because its claims stay inside its evidence. It also makes unfinished operational decisions visible: notification routing, real production account separation, retained-data policy, and any required integration/load tests. A weaker record would say “production ready” after one successful apply and hide those remaining choices.

Decide whether an extension changes the capstone's purpose

Adding a custom domain can be a focused extension to the HTTP entry point. Adding a full Kubernetes platform introduces a substantially different operating model. Both can be educational, but they should have distinct requirements, cost expectations, and acceptance evidence.

For a custom domain, verify certificate placement and validation, DNS, API mapping, expected hostname, TLS behavior, and the same release response. For a Kubernetes extension, define cluster ownership, workload delivery, identity, networking, upgrades, observability, and recovery before translating the function into a container. Do not treat either as a cosmetic resource substitution.

The reference remains intentionally small enough that one learner can trace every important dependency. Preserve that quality as you extend it. If you can no longer explain which identity reads which data or which state owns a resource, pause expansion and clarify the architecture before adding more services.

Keep a maintenance backlog tied to evidence

After the capstone review, record remaining work as concrete outcomes: connect and test an approved alarm route, verify a real integration path, review a provider upgrade, rehearse a data restore, or document a production account boundary. Give each item an owner and a reason grounded in the system's requirements.

Avoid a backlog made only of service names to add. More resources do not automatically make the project more advanced. A tested recovery procedure, a narrower permission, or a clearer module migration can demonstrate deeper engineering than another decorative architecture box.

When revisiting the project, start from its actual source, state, versions, and operating record. Recreate a fresh plan and inspect changes introduced by time, dependencies, or external actions. This habit turns a one-time lab into a maintainable system and connects the course's final project to real infrastructure practice.

12.18 Your final engineering artifact

A strong capstone submission consists of the source and dependency record, a concise architecture decision, a reviewed plan/run identity, relevant test results, the observed endpoint release, selected storage/monitoring checks, a migration continuity result, and a runbook with teardown and recovery decisions. Keep sensitive state and credentials out of the shared submission.

The supplied reference gives you all the infrastructure and local tooling needed to follow that path. The verification report states which parts were actually executed during authoring and which require your own sandbox. Use that distinction as a model for your own work: make claims as specific as the evidence, and leave the next operator with enough context to continue safely.
